# AGENTS.md — working notes for ahk

This repository is **the AHK**: the AutoHotkey engine and the box
primitives, in Rust. It was split out of `yoko-rust`, which keeps the lab
MCP server, and it is a port of the Python implementation, which now lives
in the archive (`../archived/ahk-python`).

The Rust is the implementation that runs. **The dialect is AutoHotkey
v2.0.19**: the names, the classes, the directives and the operators are
the ones the binary of v2.0.19 has, and the tables in
`crates/ahk/reference/` are read out of it.

The Python in the archive is the record of what the dialect meant before
the port to v2. It is kept to be read, not to be run. **The two do not
speak the same dialect any more, and that is the point of the port.** The
rule that said they had to agree is in section 1, and it has changed.

**The box** is the lab machine at `192.168.0.40`: Linux, a Wayland
session, the COSMIC compositor. Everything in the second part of this file
happens there, not on the workstation that edits the code.

The first part of this file is the map: the commands, the layout, the
rules. The rest is the working notes -- the things that are easy to break
by accident, each one saying what the rule is and why.

## Setup commands

- Build:         `cargo build --workspace`
- Test:          `cargo test --workspace`
- Lint:          `cargo clippy --workspace --all-targets`
- Without `std`:
  `cargo build -p ahk --no-default-features --target thumbv7em-none-eabihf`

The crates depend on each other by path, so there is nothing to install.
The runner takes a script on stdin and writes the report on stdout.

A build on the box is section 12, and it is two steps, not one: copy the
source there first, or the build compiles the sources the box still has,
and the result is a stale binary with no error.

## Project layout

- `crates/ahk/` -- the language: `lib.rs` (the public surface),
  `lexer.rs`, `ast.rs`, `parser.rs`, `runtime.rs`, `keys.rs`,
  `builtins.rs` (the built-in table), `classes/` (the class types),
  `desktop.rs` (the capability traits), `variables.rs` (the built-in
  variables), `regex.rs` (the regular expressions), `date.rs` (the date
  and the time), `files.rs` (the files of the machine), `settings.rs`
  (the settings of the script) and `hotkeys.rs` (the hotkeys of the
  script). No I/O of its own.
- `crates/ahk/reference/` -- the tables of v2.0.19: the surface, the
  operators and the pending list, and the surface of the v1.1.37.02 with
  the probe that measured it. The tables of the v2 are read when the tests
  are compiled.
- `crates/ahk-box/` -- the box primitives: `lib.rs` (the public surface),
  `keyboard.rs` (the uinput keyboard), `pointer.rs` (the absolute
  pointer), `desktop.rs` (the captures and the screen reads),
  `native.rs` (the call into a library of the machine), `raven.rs`
  (the call into a library of Windows), `files.rs` (the files of the
  machine), `hotkeys.rs` (the watcher of the keyboard) and `wayland.rs`
  (the windows of the compositor). The helper that the raven runs is in
  `crates/ahk-box/helper/`, and the XML of the Wayland protocols is in
  `crates/ahk-box/protocols/`.
- `crates/ahk-cli/` -- the runner. The binary is `ahk`.
- `crates/ahk/tests/language.rs` -- the dialect tests.
- `crates/ahk/tests/builtins.rs` -- the cases of the built-ins.
- `crates/ahk/tests/variables.rs` -- the cases of the built-in variables.
- `crates/ahk/tests/surface.rs` -- the parity with the surface of v2.
- `crates/ahk/tests/class_surface.rs` -- the probe of the class types.
- `crates/ahk/tests/class_*.rs` -- the cases of each class type.
- `crates/ahk-box/src/pointer.rs` -- the cases of the pointer ABI.
- `crates/ahk-cli/tests/runner.rs` -- the cases of the runner.
- `../archived/ahk-python/` -- the reference implementation. Frozen;
  nothing new lands there.
- `docs/ahk-x11-comparison.md` -- the AHK_X11 (the AHK v1.0.24 for X11, in
  Crystal) against this tree, and what to port from it. Read it before
  touching the hotkeys, the clipboard, the sound or the windows. Its code
  is GPL-2.0 and this tree is Apache 2.0: the behaviour may be ported, the
  code may not.
- `docs/wayland-toplevel-enumeration.md` -- how a Wayland compositor
  lists its windows, and the Rust that does it. Read it before touching
  `WinExist` or `WinActive`: the compositor of the box publishes the
  protocol, and this is the code that speaks it. The clipboard is not
  spoken through it (section 27).
- `docs/v2-capability-report.md` -- what the tree answers of the surface
  of the v2, by the area a name belongs to: the parser and the run, the
  files, the input, the windows, the screen, the native calls, the
  registry and the COM objects. It is generated by the script in
  `crates/ahk/reference/ahk-v2.0.19.areas.py` , and the state of each name
  is the one of `ahk --surface` .
- `docs/ahk-v1-dialect.md` -- the plan for the v1 dialect beside the v2:
  the gate, the phases, and what was measured on the binary of v1.1.37.02
  on 2026-10-28. Read it before touching the parser or the built-in
  table: it says where the dialect is woven into the tree. The comparison
  with the AHK_X11 says that the legacy v1 syntax is not ported; that
  line is inverted for the v1 dialect alone, and this plan is where the
  decision lives.

EGM artifact directory: `egm-review/`

The dependency runs one way: `ahk-cli` -> `ahk-box` -> `ahk`, and `ahk`
depends on nothing in the workspace. The language crate must not reach for
the box: it does no I/O, and it has to keep building without `std`.

## Code style

- The parser and the runtime do no I/O. The desktop is an interface the
  runtime is handed, which is why the language can be tested against a
  fake.
- The uinput syscalls -- opening `/dev/uinput`, writing ioctls, reading an
  event node -- are behind `#[cfg(target_os = "linux")]`, per function: on
  another target they are not compiled and the device answers `NotLinux`.
  `ahk-box/src/desktop.rs` is not behind that gate at all: it compiles on
  Windows too, and fails there when it is used.
- The language crate runs without the standard library. `ahk` has a `std`
  feature, on by default; with it off the crate is `#![no_std]` and builds
  for a target that has no `std` at all. The host then supplies one thing,
  through the `Clock` trait: the clock -- the time the runtime measures
  itself with, and the pause `Sleep` asks for. `now_ms` is the
  milliseconds since an arbitrary origin and never goes backwards;
  `sleep_ms` waits at least that long. The same clock measures the timeout
  and the steps. On a target without `std` the constructor is
  `Runtime::with_clock(desktop, clock, timeout)`; `Runtime::new` and
  `SystemClock` exist only with the feature. `ahk-box` and `ahk-cli`
  always pull `std` in, so the path without it is `-p ahk` alone. The
  crate's own doc has a worked example of the trait. The trait also
  carries the date of the machine, in `wall_clock`: it answers with
  nothing when the host does not know it, and a runtime without `std`
  that does not answer it says that it does not know the date.
- A float function that `std` owns -- `sqrt`, `floor`, `ceil`, `round`,
  `fract` -- goes through the helper in `runtime.rs`, which is `libm`
  under `no_std`. Only `abs`, `min`, `max` and `clamp` may be called on an
  `f64` directly: they are in `core`.
- The tree is not in rustfmt's shape, and `cargo fmt --all` would rewrite
  it: the code is written compactly, with a struct variant and a line of
  logic on one line, and the defaults would expand all of that into
  something else. There is no `rustfmt.toml` to say so. The formatter is
  therefore not part of the loop: match the code you see next door, and do
  not run it over the tree.
- The comments and the commits say *why*, in plain sentences, in the same
  voice as this file.
- **The documents of this repository are in English.** The `AGENTS.md`,
  the `README.md`, the contracts, the guides and the plans are all in
  English, and so are the comments of the code and the reasons that the
  runtime answers with. The owner decided it, and the documents that were
  in Portuguese were translated.
- **The built-in table is the list of what the dialect carries.** Every name
  of v2.0.19 is in `builtins.rs`, with its kind, its arity and the handler
  that answers it. A name that is shaped for Windows is in the table too,
  and the handler answers it with the reason: a question the desktop cannot
  answer fails, and it does not answer `false`.
- **The `Desktop` trait is the sum of fifteen capability traits** -- `Keyboard`,
  `Pointer`, `Screen`, `Windows`, `Processes`, `Files`, `Clipboard`,
  `Timers`, `Hotkeys`, `Native`, `Sound`, `Machine`, `Dialogs`, `Network`
  and `Pictures`. There is
  no blanket
  implementation: every implementor writes the fifteen of them, and every
  method that a
  capability does not have has a default that says so. A new capability
  goes in its own trait, and `Desktop` grows by naming it.
- **A class type of the runtime is a class too.** `Map`, `Array`, `Buffer`,
  `File`, `Func`, `Gui`, `Menu`, `Hotkey` and `Enumerator` are classes the
  script cannot extend. Their state lives in the property table of the object
  under a reserved key, and only the module that owns the class touches it.
- **The class module is asked before the base object.** A class that
  answers `OwnProps` itself is taken at its word; the base object answers
  the names every object has only when the module does not.
- **A function and a method are checked apart.** Measured on the binary
  of v2.0.19 on 2026-10-27: a function of the script called with too few
  arguments fails with "Too few parameters passed to function.
  Specifically: MyFunc". The method is checked at the run and not at the
  load, and it says so in other words: measured on the binary of v2.0.19
  on 2026-10-30, a method called with too few arguments answers "Missing
  a required parameter." and one called with too many answers "Too many
  parameters passed to function.". A parameter may carry a default
  (`Name(a, b := 1)`) or take the rest of the arguments (`Name(a,
  rest*)`), which is an array.
- **The number of the arguments is checked in two places.** Measured on the
  binary of v2.0.19 on 2026-10-29: a call that the script writes is checked
  when the script loads, and the failure names the function: "Too few
  parameters passed to function.\n     Specifically: Abs". A call that goes
  through a value is checked when the call runs, and it says so in other
  words: a built-in answers "Too few parameters passed to function." and a
  function of the script answers "Missing a required parameter.". The name
  of the function goes in the `Extra` of the error, and the name of the
  parameter that is missing goes there when the callee is a function of the
  script. The tree checks the call that the script writes at the run and
  not at the load, and it says the same words.
- **The messages of the class types are the messages of v2.** Measured on the
  binary of v2.0.19 on 2026-10-29: a key that is not there is "Item has no
  value.", a place of an array without a value is "Item has no value.", an
  array with nothing to take away is "Array is empty.", a length that is
  negative is "Invalid value.", and the capacity of a map is a number of
  thirty-two bits: a value that is out of the range wraps around, and
  `m.Capacity := -1` answers 4294967295.
- **The marker of a by-reference parameter is in the definition.** v2
  writes it on the parameter -- `Swap(&Left, &Right)` -- and the caller
  passes a reference -- `Swap(&a, &b)`. The parameter is then an alias of
  the variable of the caller: reading it reads there and writing it writes
  there. A parameter that is not written that way holds the reference as a
  value of its own, and reading it fails.
- **A reference is a value of its own kind, and v2 names it a VarRef.** It
  points at a variable by its name and by its scope, and it is neither a
  string nor a number: the operations that want one of those say that they
  got a VarRef. It is an object, though: the `IsObject` of a reference is
  one. The reference of a built-in variable, of a function and of a class is
  refused, each with the reason v2 gives.
- **The flag of the table of v2 is the place of the first parameter that is
  written back.** `builtins::reference_parameters` is that column turned into
  the places of the parameters, and a reference in any other place is a
  value where a variable is wanted.
- **The pattern of v2 is exact, and `(?i)` takes the case away.** The engine
  of the tree carries that one option of PCRE, and a pattern that asks for
  another one is refused with the reason.
- **There is no kind of command in v2.** The built-in table has a `kind`
  column, because the binary keeps its names in two tables and the
  column is the record of that. The parser decides by the syntax: a
  name at the start of a line, without parentheses, is a call statement,
  and the v2 documentation says that every function may be written that
  way -- a built-in and a function of the script alike. `Abs 5` is a
  valid v2 script.
- **A name that is a statement is a call.** Measured on the binary of
  v2.0.19 on 2026-10-29: `m.Method` as a statement calls the method with no
  arguments, and the parentheses may be left out -- `t.Method` answers
  "Missing a required parameter." when the method wants one. A property is
  not a method: `m.Count` as a statement answers "This value of type
  \"Map\" has no method named \"Count\".". An item is not a call:
  `m["a"]` as a statement reads the item, and the value it leaves behind is
  not used. In an expression the rule is the other way round: `y := m.Count`
  reads the property, and `y := t.Method` hands the method over.
- **A parameter that the tree cannot honour fails with the reason.** The
  arity in a row is the arity of the binary, so a call that asks for
  more than the tree can do is taken by the table and refused by the
  handler. It is never ignored: a call that answers with a wrong value
  and says nothing is the worst outcome.
- **An item is written by the class that owns it, and only by that one.**
  Measured on the binary of v2.0.19 on 2026-10-27: `m["a"] := 1` writes an
  entry of a `Map` and `a[1] := 5` writes a place of an `Array` whose
  index is already there. A class of the script has no way to write one:
  `__Set` is not called for it, and `x[y]` asks only the `__Item`, which
  reads and never writes. The tree follows that, and a class that cannot
  write an item fails the statement with the reason.
- **An object is called through its `Call` method.** Measured on the binary
  of v2.0.19 on 2026-10-30: `o(2, 3)` asks the `Call` method of the
  object, and refuses with "This value of type \"Plain\" has no method
  named \"Call\"." when there is none. The `__Call` of a class is for a
  method that is not there: `o.Unknown(2, 3)` asks it with the name of
  the method and the parameters of the call.
- **The meta-functions take the parameters of the access.** Measured on the
  binary of v2.0.19 on 2026-10-30: `__Get(Name, Params)` and
  `__Set(Name, Params, Value)`, where `Params` is an array of the
  parameters between the brackets. The name is the name the script wrote.
  The meta-function handles the whole access: the answer of `__Get` is the
  answer of `x.y[z]` and not an item of it. The tree asked `__Get` with
  the name alone, and `__Set` with the name and a zero instead of the
  value that is written.
- **A variable that has no value is named after its kind.** Measured on the
  binary of v2.0.19 on 2026-10-30: "This global variable has not been
  assigned a value." for a variable of the script, and "This local
  variable has not been assigned a value." for a variable of a function.
  The tree named the variable and not its kind.
- **The error object carries the `What` and the `Extra` of v2.** Measured
  on the binary of v2.0.19 on 2026-10-30: `Error(Message, What, Extra)`
  makes an error, and the catch holds it. An error thrown inside a
  function of the script carries the name of the function in its `What`,
  and one thrown inside a method carries "Thing.Prototype.Method". The
  error of the arity of a method carries the name of the parameter that
  is missing in its `Extra`, or the name of the method. A runtime error
  in an expression carries no name at all. The stack of v2 is not
  carried: the script of the runner has no file.
- **The failure of a class type names the member that raised it.**
  Measured on the binary of v2.0.19 on 2026-10-30: the failure of a
  method of a class type carries the name of the method in the `What` --
  "Map.Prototype.Get", "Map.Prototype.__Item.Get",
  "Array.Prototype.Length.Set" -- and the value that failed in the
  `Extra`: the key of a map, the place of an array. The number of the
  arguments of a call is checked when the script writes it, and the
  failure carries the name of the method in the `Extra` and nothing in
  the `What`: "Map.Prototype.Get". The call of the `Call` method of a
  value carries that method in the `What`: "Func.Prototype.Call". The
  numbers of the arguments are in `classes::CALLS`.
- **The failure of a built-in names the built-in.** Measured on the
  binary of v2.0.19 on 2026-10-30: the failure of a built-in carries the
  name of it in the `What` -- "Chr", "FileOpen", "WinActivate" -- and the
  value of the parameter that failed in the `Extra`: "Parameter #1 of
  Chr is invalid." carries "-1". The failure of the machine is of the
  class `OSError`, and its message is the code of the system in front of
  what it says: "(2) The system cannot find the file specified.".
- **The errors of v2 are a tree of classes.** Measured on the binary of
  v2.0.19 on 2026-10-29: the classes are `Error`, `MemoryError`,
  `OSError`, `TargetError`, `TimeoutError`, `TypeError`, `UnsetError`,
  `MemberError`, `PropertyError`, `MethodError`, `UnsetItemError`,
  `ValueError`, `IndexError` and `ZeroDivisionError`, and every one of
  them is made the way `Error` is: `TypeError(Message, What, Extra)`. A
  message that is not given is the name of the class, and the name of
  the class is the one of v2: `TypeError`, and not `Typeerror`.
- **A failure of v2 is of a class of its own.** Measured on the binary of
  v2.0.19 on 2026-10-29: a property that is not there is an `UnsetError`,
  a `MemberError` and a `PropertyError` at the same time, and an index
  that is out of range is a `ValueError` and an `IndexError`. The classes
  derive from one another, and every one of them is an `Error`. The tree
  carries the classes and the tree of them, and the class of a failure is
  decided by the message of it, the way v2 decides it by the kind of the
  failure: a division by zero is a `ZeroDivisionError`, a property that is
  not there is a `PropertyError`, a method that is not there is a
  `MethodError`, an item that has no value is an `UnsetItemError`, an
  index that is out of range is an `IndexError`, a value of the wrong type
  is a `TypeError`, and a value that is not valid is a `ValueError`. The
  failures of the files are still of the class `Error`: the message of the
  machine is not the one of v2, and the class of those failures is not
  carried yet.
- **A method of the script is a value.** Measured on the binary of v2.0.19
  on 2026-10-30: `t.Method` hands over a function whose name is
  "Thing.Prototype.Method", and the reference is the method itself: the
  first argument of the call is `this`, and a call without one answers
  "Missing a required parameter.". The method of the class and not of an
  instance is not handed over: `Thing.Method` answers "This value of type
  \"Class\" has no property named \"Method\".". The methods of the class
  types of the runtime are handed over as well, since 2026-10-29.
- **A method of a class type is a value, with the name and the arity of
  v2.** Measured on the binary of v2.0.19 on 2026-10-29: `m.Clear` hands
  over a function whose name is "Map.Prototype.Clear", and the first
  argument of the call is the object itself. The number of the arguments
  is the one of the binary: `m.Get` takes two and gives three, because
  the default of the key is an argument as well. A class is not an
  instance: `Map.Clear` answers "This value of type \"Class\" has no
  property named \"Clear\".". The table of the numbers is in
  `classes::METHODS`.
- **A class type is made the way v2 makes it.** Measured on the binary
  of v2.0.19 on 2026-10-30: a function and a file are not made at all,
  and the call answers "Invalid base.", of the class `ValueError`, with
  the name "Object.Call" in the `What` -- the call goes through the base
  object, and the base of them has no such thing. The number of the
  arguments of a constructor is checked, and the failure carries the
  call in the `What` ("Buffer.Call", "Gui.Call", "Menu.Call",
  "Object.Call") and the constructor in the `Extra`
  ("Buffer.Prototype.__New", "Error.Prototype.__New"). The type of an
  argument is checked too: `Buffer("x")` answers "Parameter #1 of
  Buffer.Prototype.__New requires a Number, but received a String.", of
  the class `TypeError`, with the value in the `Extra`. The number of the
  parameter counts the base of the class in the `Gui` and not in the
  `Buffer`. The table of the constructors is in
  `classes::CONSTRUCTORS`. The options of a `Gui` are not read yet: the
  tree takes any text, and v2 refuses the ones it cannot read with
  "Invalid option.".
- **The star is the console of the machine.** Measured on the binary
  of v2.0.19 on 2026-10-30: `FileAppend "hello", "*"` writes to the
  standard output, and `FileOpen("*", "w")` opens it as a file: the
  writes go to the standard output, the reads answer an empty text, and
  the length of the file is the number of the characters that were
  written to it. The tree has no console of its own: the output of the
  script is the output of the report, the same place where the message
  of a `MsgBox` goes. The answer of the `FileAppend` is an empty text:
  v2 gives nothing back.
- **The operations on a file that is closed answer with a value.**
  Measured on the binary of v2.0.19 on 2026-10-30: a read of a file
  that is closed answers an empty text, and the reads of the numbers
  answer it too; a write answers the number of characters it wrote, and
  the writes of the numbers answer the number of bytes; `Seek` answers
  zero, `Pos` answers minus one, `Length` answers zero, `AtEOF` answers
  one and `RawRead` answers zero. The mode of the file says what may be
  done with it: a file that is opened to be read cannot be written, and
  a file that is opened to be written cannot be read, and v2 does not
  fail either way. The write of a text answers the number of characters
  and not the number of bytes, and the raw write of a text writes the
  bytes of the UTF-16. The encoding of a file is not carried yet: the
  tree knows UTF-8 and UTF-16, and v2 knows the code page of the
  machine.
- **Every value carries its class.** Measured on the binary of v2.0.19
  on 2026-10-30: the `__Class` of a value is the name of its class ---
  "Integer", "Float", "String", "Array", "VarRef", the name of the class
  of the script --- and a class is a class of its own kind: "Class". The
  prototype of a class is of the class it is the prototype of: "C",
  "Map". The class of a value that is not an object cannot be written:
  "Property is read-only.", with the name of the property in the `Extra`.
  On an object it is written like any other property, and it shadows the
  class of the value. Every object has the property, and it is not an own
  property: `m.HasProp("__Class")` is 1 and `m.HasOwnProp("__Class")` is
  0.
- **The pictures of the machine are the machine's.** Measured on the
  binary of v2.0.19 on 2026-10-29: the `LoadPicture` takes three
  parameters and answers the number that identifies the picture -- zero
  when the picture could not be loaded, and not a failure -- and the type
  of the handle is written in the third parameter. The `ImageSearch`
  takes seven parameters, the first two of them by reference, and it
  answers one when the picture is on the screen and zero when it is not,
  and the place of the picture is written in the first two variables of
  the caller. A picture that cannot be loaded is refused with "Parameter
  #7 of ImageSearch is invalid.", and a value where a variable is wanted
  is refused with "Parameter #1 of ImageSearch requires a VarRef, but
  received an Integer.". The images are read by the desktop, and the box
  reads them with the `png` crate: it looks for them on the screen with a
  capture of `grim`.
- **The download is the machine's.** Measured on the binary of v2.0.19 on
  2026-10-29: the `Download` takes two parameters -- the url and the
  name of the file -- and it answers nothing: the answer is an empty
  text. A file that is not there on the network is not a failure either:
  the server sends its page of the error, and that page is what is
  written. A url that cannot be reached at all fails with a failure of
  the class `OSError`, and the message is the code of the machine in
  front of what it says: "(12006) ". The network is a capability of the
  desktop, and the box fetches the file with curl.
- **The questions of the user are the machine's.** Measured on the binary
  of v2.0.19 on 2026-10-29: the three dialogs of v2 are `InputBox`,
  `FileSelect` and `DirSelect`, and they take four, four and three
  parameters. The `InputBox` answers an object of the class `Object`, and
  the object carries the text of the user in its `Value` and the way the
  dialog ended in its `Result`: "OK", "Cancel" or "Timeout". The
  `FileSelect` answers the path of what the user chose, and it is an array
  of the paths when the user may choose more than one. The `DirSelect`
  answers the path of the folder. The options are read by the runtime,
  because they are the dialect's: an option of an input box that v2 does
  not know is refused with "Invalid option.", of the class `ValueError`,
  and the option that was not known is in the `Extra`; an option of a file
  selection that v2 does not know is refused with "Parameter #1 of
  FileSelect is invalid."; the filter of a file selection is not there
  when the user chooses a folder, and it is refused with "Parameter #4 of
  FileSelect is invalid."; and the options of a `DirSelect` are a number,
  and a text that is not one is refused with "Parameter #2 of DirSelect
  requires a Number, but received a String." The window is the machine's:
  the `Dialogs` trait is a capability of the desktop, and the box asks
  the user through zenity -- the exit code of zenity says how the dialog
  ended, and the timeout of the options of v2 is the timeout of zenity.
- **The refusal of an object is the wording of v2.** Measured on the binary
  of v2.0.19 on 2026-10-30: `x.nothing` on a number answers "This value of
  type \"Integer\" has no property named \"nothing\".", `x.nothing()` answers
  the same with "method" where the property says "property", and `x[1]`
  answers "This value of type \"Integer\" has no property named \"__Item\"."
  -- the item is the `__Item` of the value, and that is the name the
  refusal carries. The type is the class of the script, the name of the
  class type, or the kind of the value: "Thing", "Map", "String", "Float".
  A property that is written is refused the same way, and a text has no
  item at all: `SubStr` is the way to take a letter out of one.

## Testing instructions

- `cargo test --workspace` -- the dialect tests. They need no box: the
  desktop is a fake that records the calls.
- The Rust suite was the port of the dialect cases, and it is not a copy of
  the archived suite: the archive has cases for the pointer, the CLI and
  the MCP addon that have no Rust counterpart, and the Rust suite has
  builtin cases the archive does not have. The parser and lexer cases are
  the archive's, and in Rust they live in the source files, not in
  `tests/language.rs`. **Since the port to v2 the two trees do not speak
  the same dialect, so a name that is in one and not in the other is not
  a bug any more**: v2's names are the ones that are here, and the cases
  of the archive that are about the old names stay in the archive.
- **The parity with v2 is a test of its own.** `tests/surface.rs` reads the
  surface table and asks the tree, name by name, whether it carries it: the
  built-in table for the commands and the functions, the table of the
  built-in variables for the variables, and the class types for the
  methods. A name that the tree does not carry has to be in the pending
  table, with the reason.
- **The class types are probed, not counted.** `tests/class_surface.rs`
  asks every name of every class of the surface, as a call and as a read,
  and the answer may not be "this value has no such method": the class does
  the thing or it says why it cannot.
- Where a case goes depends on what it is about: a statement goes in
  `crates/ahk/tests/language.rs`, a builtin in `crates/ahk/tests/builtins.rs`,
  a built-in variable in `crates/ahk/tests/variables.rs`, a class type in
  `crates/ahk/tests/class_*.rs`, a grammar rule in `parser.rs`, a token in
  `lexer.rs`, a key in `keys.rs`. The ported archive cases are in those
  places.
- A new language feature gets its cases in the Rust tree. **Not** in the
  archive: that tree is frozen, and it is the record of what the dialect
  meant at that point. The README of this repository still says the
  opposite on this point; this file wins.
- The guard rails and the timeout are language cases too, and they are in
  `tests/language.rs`: a script that loops forever must fail with `error`
  holding "ran more than" and `error_line` set. The timeout is the odd one
  out: it stops the script between two statements, so it knows no line,
  and `error_line` is null.
- The runner's exit codes and the pid file are not language cases: they
  are in `crates/ahk-cli/tests/runner.rs`, next to the cases of the
  archived Python runner.
- The pointer's numbers are in `crates/ahk-box/src/pointer.rs`: the ioctl
  requests, the sizes of the structs they carry, the codes and the clamp.
  Those are the numbers that fail silently, with an `EINVAL` and nothing
  else, so they are pinned against the C definitions here and not on the
  box. The archive's addon cases have no place in this tree: the addon
  lives in `yoko-rust`. The device itself is checked on the box, by hand:
  section 12.

## The guard rails

The runtime stops a script that does not finish, and says so when it does.
A limit is reported as an `error` with the line of the statement that
tripped it.

- `Runtime::MAX_STEPS` -- 20 000 statements in one script. The statement
  that would have been the 20 001st is the one reported: "the script ran
  more than 20000 statements".
- `Runtime::MAX_ITERATIONS` -- 1 000 turns through a `While` body: "the
  loop ran more than 1000 times". A counted `Loop` has no iteration guard
  of its own: it is bounded by the step count and by the timeout. A `Loop`
  without a count is bounded by the step count too, and it counts each of
  its turns as a statement, because the body of it may be empty and the
  step count is the bound that still moves.
- `Runtime::MAX_DEPTH` -- 1 000 nested calls. v2.0.19 stops at about 1 105,
  and it says "Function recursion limit exceeded."; the tree stops at the
  same place and says the same thing.
- The stack is the other bound of a recursion. The frames of the tree are
  heavier than the ones of v2 -- about 50 KB of stack per call in a debug
  build and about 5 KB in a release build -- so a host with a small stack
  would run out of it before the depth says so. `Runtime::MAX_STACK` is how
  much stack a run may use (512 KB, when the host does not say), and
  `with_stack_budget` is how the host says otherwise. The runner gives its
  thread 128 MB of stack and says 64 MB.
- `Sleep` is capped at 60 000 ms, in the statement and in the builtin.
- The timeout is the other bound: `--timeout=N` on the runner, in seconds,
  60 by default. It is checked before every statement, so a `Sleep` can
  overshoot it. The message is "the script ran for more than Ns" and
  `error_line` is **null**: the timeout path never sets it.

The runner's exit code is 0 when the script finished, 1 when it failed,
and 2 when it did not parse. The report is JSON on stdout in every case
but one: if the script cannot be read from stdin, the runner writes the
reason to stderr and exits 2 without a report.

## The surface of v2

The dialect is AutoHotkey v2.0.19, and the tables in
`crates/ahk/reference/` say what that means. They are read out of the
binary of v2.0.19, and they are the contract of the port.

- `ahk-v2.0.19.surface.tsv` -- every name of v2: its kind (`command`,
  `function`, `variable` or `method`), the class a method belongs to, and
  the address of its handler in the binary.
- `ahk-v2.0.19.operators.tsv` -- the operators and their token kinds. The
  kinds are **not** a precedence: the precedence is the table in
  `ahk::precedence`, which follows the documentation of v2.
- `ahk-v2.0.19.pending.tsv` -- the names of v2 this tree does not carry
  yet, with the reason. It is empty: the port carries the whole of v2.
- `ahk-v1.1.37.02.surface.tsv` -- the surface of the v1, measured on the
  binary on 2026-10-29 with the probe beside it: the kind of each name,
  the arity of each parameter and the shape of each one (Value, Variable
  or Output). A directive has no shape: every parameter of a directive is a
  value, and a directive is not a row of the built-in table. The plan of the
  dialect is `docs/ahk-v1-dialect.md`, and the gate is not built yet: the
  table is the data of its first phase.
- `ahk-v1.1.37.02.pending.tsv` -- the names of the v1 that the tree does
  not carry yet, with the reason. It is not empty: it is the first pending
  table that is not, and it has 72 names.

**The tree does not carry a name that v2 does not have.** Measured on
the binary of v2.0.19 on 2026-10-30: a file has no `ReadUInt64` and no
`WriteUInt64`, and it is not made again. The tree carried all three
until 2026-10-30, and refuses them the way v2 refuses them now.

**A name is carried when the tree answers it.** The answer may be a value
or the reason the tree cannot give one. A name that is shaped for Windows
is carried the same way, and it is not pending: a script that asks for
`ControlSendText` is told what the desktop of this tree cannot do, and not
that the answer is `false`.

**Linux is the focus, and Windows is kept.** The box is a Linux desktop,
and the primitives of the box are the Linux ones: the uinput keyboard,
the absolute pointer, the `grim` capture. The names of v2 that are about
Windows stay in the surface all the same, and they answer with the
reason they cannot answer: a script that calls `ControlSendText` runs,
and it is told what the desktop of this tree cannot do. The `DllCall` is
the one that is not refused: it calls the library of the machine, and it
does it on Windows and on Linux (section 23). The names are the names of
v2 on every platform, and the desktop is the one thing that differs.

**The tables are read when the tests are compiled**, so a name that moves
between them breaks the build of a test and not a run of it.

### The tables that the extraction read at the wrong place

The extraction that read the tables out of the binary got two of the class
tables wrong and left nine class types out, and the tree would have carried
the wrong names with it.

- **The `Buffer` table.** The extraction gave it fifteen rows: `Ptr`,
  `__Item`, `__New`, `__Enum`, `__Get`, `Count`, `Len`, `Mark`, `Name` and
  `Pos` among them. Measured on the binary of v2.0.19 on 2026-10-27 with
  `HasProp` and `HasMethod`, a buffer has **`Ptr` and `Size`** and the
  method **`__New`**, and nothing else: `Pos`, `Len`, `Mark`, `Name`,
  `Count`, `__Get`, `__Set`, `__Enum` and `__Item` are all absent. The
  table was read at the wrong place.
- **The `Array` table.** All thirteen of its rows carry one handler
  address, and the `Buffer` table carries one for its last eight rows: a
  table whose members are methods and properties mixed cannot have one
  handler for all of them. The names of the array are right, and the
  handlers were not resolved.

- **The `Func` table.** Its last four rows were read at the wrong place:
  `__New` twice, `Ptr` and `Size`, each with an address of its own.
  Measured on the binary of v2.0.19 on 2026-10-30: a function has no
  `Ptr` and no `Size` --- `f.Ptr` answers *"This value of type "Func" has
  no property named "Ptr"."* --- and it is not made again: `f.__New()`
  answers *"This value of type "Func" has no method named "__New"."*.
  The tree does not carry the three names since 2026-10-30, and it
  refuses them the way v2 refuses them.
- **Nine class types are not in the table at all.** Measured on the binary
  of v2.0.19 on 2026-10-29: `Menu` , `ComObject` and the seven error
  classes --- `TypeError` , `ValueError` , `OSError` , `TargetError` ,
  `TimeoutError` , `PropertyError` and `MethodError` --- are in the binary
  and are not in `ahk-v2.0.19.surface.tsv` . The seven error classes each
  carry the same six properties --- `Message` , `What` , `Extra` , `File` ,
  `Line` and `Stack` . The tree carries the `Menu` --- it is the menu of a
  window, and it refuses with the reason of the windows --- and it carries
  the classes of the errors since 2026-10-29: `TypeError("boom")` makes an
  error of the class `TypeError`. It carries none of the `ComObject`:
  `ComObject("Shell.Application")` still fails with *"Call to nonexistent
  function."* . The `Error` itself is not in the table either, and the tree
  carries it since 2026-10-30: `Error(Message, What, Extra)` makes an
  error, and the catch holds it. The stack of v2 is not carried.

The lesson is in the tree now: the probe of `tests/class_surface.rs` asks
the tree what it answers, and the answer is what counts -- not the
address in the table. The report of the areas says what the tree answers
of every name, and it is `docs/v2-capability-report.md` .

## 2. The uinput syscalls only run on the box

Everything that opens `/dev/uinput`, writes ioctls, or reads an event node
is behind `#[cfg(target_os = "linux")]`. The crate still compiles
elsewhere: the gated parts answer `NotLinux` -- "the keyboard is a Linux
uinput device; this is not Linux" -- when they are used. The writing of
the events is compiled everywhere; it simply cannot reach a device that is
not there.

The build on the box, and the check that matters, are section 12.

## 3. The uinput devices have to declare what they are

An event travels: the kernel reads our device, libinput turns it into a
description for the compositor, and the compositor hands the key to the
client -- the application the user is looking at. A device declares what
it can do -- its key codes and its flags -- and the compositor builds its
keymap from that declaration. A wrong declaration is accepted by the
kernel and stops at the compositor.

- **The virtual keyboard declares the same 112 codes as the box's physical
  keyboard.** The list was read out of `/proc/bus/input/devices` on
  2026-10-25 (the `AT Translated Set 2 keyboard`). With a sparse list, or
  with codes a real keyboard does not have, libinput builds a keymap it
  cannot use: the key events arrive at the compositor and are reported
  with the key code `-1`, which a client cannot use. The events are in the
  event node the whole time -- `cat /dev/input/eventN` shows them -- and
  they stop there.
- **The scan codes ride with the key events.** The device emits
  `EV_MSC`/`MSC_SCAN` before each key event -- the kernel's channel for
  the hardware scan code -- and declares the `MSC_SCAN` bit in its
  capabilities.
- **The pointer announces `INPUT_PROP_DIRECT` and absolute axes**, like
  the device Sunshine creates on that box. ydotool's device is a
  *relative* mouse with a full keyboard key bitmap and no
  `INPUT_PROP_POINTER`, so libinput classifies it as a keyboard and
  ignores the relative axes: the click arrives and moves nothing.
- **The pointer is a device of its own.** libinput picks one role per
  device, and the role with the richer key bitmap wins, so the keyboard
  and the pointer cannot be one device.

The numbers behind that -- the ioctl requests and the sizes of the structs
they carry -- are pinned by the cases in `pointer.rs`. They fail silently,
with an `EINVAL` from the kernel and nothing else, so a mistake in them is
caught on the workstation and not on the box.

## 4. The waits the box needs

- **A new device needs four seconds before the compositor adopts it**
  (`ENUMERATION_WAIT`, in `keyboard.rs`). A click that arrives before the
  compositor adopts the device lands nowhere -- and the report still says
  the click happened, because the device accepted the event even though
  the compositor ignored it. The keyboard and the pointer both wait. *The
  archive's pointer constant says five seconds (`src/ahk/box.py:131`),
  although its own rule says four; the Rust waits four, the number the box
  was measured with. Open: whether the pointer needs five.*
- **The pointer needs 200 ms between the motion and the press**
  (`PRESS_SETTLE`, in `pointer.rs`). A press that arrives in the same
  frame as the motion is applied at the position the pointer had before
  the motion. Measured on 2026-10-25: with a 20 ms gap the click landed
  hundreds of pixels away from where it was aimed.
- **A client coalesces a burst of key events** (`KEY_GAP`, 20 ms). A
  hundred backspaces that arrive back to back are counted as a handful,
  not as a hundred. Measured on the lab box on 2026-10-25, a client lost
  most of a burst of 320 backspaces; with this gap between the release and
  the next press, every one of them counts.
- **A key stays down for 20 ms** (`KEY_HOLD`) and **the button for 40 ms**
  (`PRESS_HOLD`): long enough for the compositor to see the press, short
  enough that the auto-repeat never starts.
- **The kernel does not repeat an axis value that did not move.** The Rust
  pointer moves once and then presses, so a click at the position the
  pointer is already at carries no motion with it. Whether the click still
  lands in that case is **open**: it has not been measured.

## 5. The text goes through our own keyboard

`ydotool type` was exact while `ydotoald` was running on that box. It is
not any more: `/usr/bin/ydotoald` was removed from the disk of that box,
the process that was still running has died, and `ydotool type` without a
daemon writes into a socket nobody is listening on and reports nothing.

**`ydotool key` is never used.** ydotool 1.x reads a key *name* as zero
and does nothing at all (the command exits 0 and the screen does not
change), and a numeric *code* presses the key without ever releasing it,
so the compositor's auto-repeat types it forever. One `ydotool key 22`
produced about a hundred and thirty `u`s and left the key held, on
2026-10-25. The modifier suffix (`30:1` for ctrl+a) is not understood at
all.

**The text is typed one key at a time, through the keyboard of our own,
and the layout is the US one.** A character the layout does not have fails
the statement with "the keyboard of this box has no key for it" -- it is
not typed as something else.

## 6. Modifiers reach the client

An earlier version of this file said "a modifier never reaches the client
on this box". That was measured with the **ydotool** device, whose
`key 30:1` ignores the suffix: the chord was never sent.

With a keyboard of our own the chord is sent -- the modifier goes down,
the key goes down, the key comes up, the modifier comes up -- and a client
acts on it: measured on 2026-10-25, `ctrl+a` selected the text of a GTK
field and the next key replaced it; measured again on 2026-10-27, `ctrl+a`
selected the text of a field of the Steam store window and a backspace
deleted it.

**The shift key is what makes capitals work** in the text path, and it
works for the same reason.

## 7. The focus check, and the windows of the compositor

`PixelGet` and `PixelSearch` are read from the screen, so they work
whatever window is in front. `MouseGetPos` is not: it reads the position
of the pointer this runtime drives, which is the only pointer on that box
whose place can be read at all -- the physical mouse is relative, so its
place cannot be read.

**The windows of a Wayland session are asked of the compositor, and the
compositor answers.** Measured on 2026-10-29 on the box: `WinGetTitle()`
answered `pod153/Login - Chromium`, `WinExist("Chromium")` answered 1,
`WinExist("chromium")` answered 0, `WinExist("zzz-nothing-zzz")` answered 0
and `WinActive("Chromium")` answered 1. The client is in
`crates/ahk-box/src/wayland.rs`, and it speaks two protocols:

- `ext_foreign_toplevel_list_v1` -- the portable one. It lists the toplevels
  and says what each of them is: the title, the application id and an
  identifier that is stable while the window lives.
- `zcosmic_toplevel_info_v1` -- the one of COSMIC, which **extends** the
  listing. For a handle of the listing the compositor gives a handle of its
  own, and that one carries the state of the window -- and the state is what
  says whether the window has the focus. The correlation is by the handle,
  so it is exact, and not a guess by title.

The XML of the two protocols is vendored in `crates/ahk-box/protocols/` and
the bindings are generated by `wayland-scanner` at build time. The
`cosmic-protocols` crate is GPL-3.0 and is **not** a dependency of this
tree: the behaviour is ported and the code is not copied. The XML is MIT.

**The state of a window comes a frame later, and the client waits for it.**
The compositor says the state in its next refresh, and a refresh is a frame
away: measured on 2026-10-29, the answer was there on the second question,
ten milliseconds after the first one. The client waits up to 250 ms, five
milliseconds at a time, and a window whose state did not arrive leaves the
question about the focus open: the answer is the reason, not a wrong window.

**The title is matched the way v2 matches it.** The mode of v2 is the
default one, 2: the title of the window has to *contain* the text that was
asked for, and the case matters -- "the window titles and text are
case-sensitive". `SetTitleMatchMode` is not carried, so the mode 2 is the
one that is used.

**A window that is not there is not a failure.** The desktop says that the
window is absent, `WinExist` answers 0 and `WinActive` answers 0. Only a
question the desktop cannot answer at all fails, with the reason.

The X11 path is kept for an X11 session, and it is the path that answers
"unknown" on this box: the session is Wayland, the COSMIC desktop's D-Bus
service answers `Introspect` with an empty list, and the Xwayland server
beside it (gamescope's rootless X server) reports an empty client list. The
Wayland path has the precedence when `WAYLAND_DISPLAY` is set. The guide is
`docs/wayland-toplevel-enumeration.md`; it carries the Rust that does it.

## 8. The emergency stop

A script that types forever has to be stoppable from outside, and the only
thing that can stop it is the process.

The runner writes its pid to `$XDG_CACHE_HOME/ahk/run.pid`, or to
`$HOME/.cache/ahk/run.pid` when that variable is not set, and removes it
when the script ends. A host with neither -- a Windows one that nobody
configured -- gets the temporary directory, and never the working
directory: the file has to be where the stop looks for it, and the working
directory changes from one call to the next. The `ahk_stop` tool of the
lab MCP (in the `yoko-rust` repo) reads that file, sends `TERM`, then
`KILL`, then sweeps up whatever is left.

Three things about that file:

- **It is written only after the script parses.** A script that does not
  parse leaves no file at all. The write itself is not checked: a run
  whose pid file could not be written is not stoppable by this route, and
  says nothing.
- **It can be stale.** A process killed by a signal never runs the
  destructor that removes it, and the runner installs no signal handler.
  The file can then hold the pid of a process that is gone -- and pids are
  reused. The `ahk_stop` tool of the lab MCP checks the pid before it
  kills anything: the pid has to be a live process whose command line
  names the runtime. A pid that is not that is reported as stale, the file
  is removed, and nothing is killed.
- **The slot is for one runner.** Two runs on the same box write the same
  file, and the first one to end deletes the second one's file.

From a shell, when the MCP itself is stuck and cannot answer:

```sh
ssh danalec@192.168.0.40 'pkill -f release/ahk'
```

That kills every `ahk` process of that user, not just the runaway one:
`pkill -f` matches the whole command line. The two other bounds are
`--timeout` and `MAX_STEPS`.

## 9. The traps of the environment probe

The environment probe is the command that reports the session in a fixed,
positional format: the screen geometry, and the environment every Wayland
tool needs. The format is positional, so the arguments have to be given in
the order it asks for.

- **The arguments are in the order the format asks for them.** In the
  wrong order the environment is set to the wrong values, and every
  Wayland tool on the box fails to connect without saying why.
- **`~` is not expanded inside quotes.** A quoted `~` is a file named `~`,
  and the shell says "no such file or directory". The path of the runtime
  is passed unquoted for that reason.
- **The geometry goes after the command, not before it.** The environment
  goes before the command: `env ... -g ...` would ask `env` to run a
  program called `-g`.
- **The box has BusyBox, not GNU coreutils.** `base64` has no `-w0` (pipe
  it through `tr -d '\n'`), `ls` has no GNU options, and there is no
  `pgrep -o` (oldest process first).
- **`grim -o` is the output *format*, not the file.** `grim -o /tmp/x.png`
  answers "unknown output". The file is the argument: `grim /tmp/x.png`.
  grim is the screenshot tool, and `grim -` writes the PNG to stdout.

## 10. What the report says

A script that drives a desktop has to be able to say what it did, not just
that it finished.

- Every statement that *completes* produces a step: the line, what it did,
  how long it took. A statement that fails stops the script and is
  reported once, in `error` and `error_line` -- it is not a step, and `ok`
  is true on every step that exists. A client that looks for the failure
  in `steps` will not find it; it has to read `error`.
- The `notes` are the places where the box was not what the script assumed
  -- the environment that was found, the device that had to be waited for.
  The runtime writes its own notes with `Runtime::note`, and the runner
  adds the notes of the box to them.
- A question that cannot be answered fails, with the reason. It does not
  answer `false`. A window that is not there is not a question that cannot be
  answered: `WinExist` and `WinActive` answer 0 (section 7).

The report is JSON on stdout: `ok`, `steps`, `output`, `notes`, `error`,
`error_line`, `exit_code`, `elapsed_ms`, `variables`. `exit_code` is what
`ExitApp` set, not the exit code of the process: the runner still exits 0.
A parse error is a reduced payload -- `error`, `error_line`, `column`,
`steps`, `output`, `notes` -- with no `elapsed_ms`, `exit_code` or
`variables`.

**The server takes the crate by path, so it breaks when the shape of this
tree changes.** The port to v2 did exactly that: a command is a call now,
and the nodes `Send` and `Click` are gone, so the arms of the sibling that
named them did not compile and the server did not build. The sibling was
fixed in its own tree, in the same week -- its own notes say that it may
be changed freely -- and the fix was three arms and two helpers.

So a change to the public shape of this crate -- a node that is gone, a
name that is renamed, a trait whose methods change -- has to be checked
against the server that depends on it:

```sh
cd ../yoko-rust && cargo check --locked --offline --workspace --all-targets
```

The failure is a compile error and not a wrong answer, so it cannot pass
unnoticed: the server does not build, and the tool that drives the box is
not there.

## 14. Where the archive and this tree differ

The rule was that they agree, and the port to v2.0.19 is what broke it.
These are the places where they differ:

- **The dialect.** The names here are the names of v2.0.19: `MsgBox` and
  not `Msg`, `StrUpper` and not `Upper`, `PixelGetColor` and not
  `PixelGet`. The archive keeps the old ones, and it is frozen there.
- **The interpolation.** The archive writes `%name%` inside a string and
  the value of the name goes there. v2.0.19 does not: measured on the
  binary on 2026-10-27, `"var:%x%"` is the text `var:%x%`. The tree keeps
  the interpolation of the archive, and it happens where the literal is
  written, so a string a function returns still knows its own parameter.
  This is the one place where the tree is deliberately not v2.
- **`Screenshot`** is a name of the dialect that v2 does not have. It is
  in the built-in table and it is listed in `tests/surface.rs` as the one
  name the dialect invents.
- **The classes.** The archive has no class types; the eleven tables of
  the binary are here now.
- **The tree has the array literal and the `for` loop.** They came on
  2026-10-28, and section 22 says how they read. The tree still has no
  exceptions, no `global` and no `until`: v2 has `try`, `catch`,
  `finally` and `throw`, a `global` that makes a variable of a function
  the variable of the script, and a loop that runs until a condition is
  true. A script that uses them fails to parse, and the reason is that
  the name is neither a built-in nor a function of the script.
- **`yield` is not in the tree.** v2 has it: a function that yields gives a
  generator, and a class that enumerates one is a generator of its own.
  The tree has no `yield`, so a class cannot write an `__Enum` that yields.
  The word is not a name of v2 either -- it is a word of the language -- so
  the tables of the surface do not carry it.

And these are the places where the two still differ in the box, each one
a bug in the port until it is measured on the box:

- **The pointer is optional in the archive and mandatory here.** The
  archive catches a pointer that cannot be created, notes it, and falls
  back to `ydotool mousemove --absolute`. The Rust propagates the error
  and the click fails. There is no `ydotool` fallback anywhere in this
  tree.
- **`Run` has no timeout here.** The archive runs the command with
  `timeout=120`; the Rust waits for it. The script's own timeout is
  checked between statements, so a `Run` that hangs past it produces no
  report at all.
- **`ensure_session_env` overwrites `XDG_RUNTIME_DIR` here.** The archive
  only sets it when it is not set already.
- **The archive's pointer can be closed, and this one cannot.** The
  archive raises an error when a closed pointer is asked to move; the Rust
  `Pointer` holds the file of the device, so there is no such state to be
  in.
- **The pointer's enumeration wait**, in section 4.

## 15. The loop over the files

Measured on the binary of v2.0.19 on 2026-10-27, with probes that were run
against the real thing.

- **`Loop Files` takes the pattern first and the mode second.** The folder
  is the one the script runs in, and it is not a parameter: `Loop Files
  "*.txt"` walks the working directory. The tree had the shape of v1,
  with the folder first, and a v2 script failed on it.
- **The mode is a set of flags.** "R" walks into the subfolders as well,
  and "D" gives the directories instead of the files. The letters are
  read without regard to the case, and a third parameter is refused:
  "\"Loop Files\" accepts at most 2 parameters."
- **The loop writes the variables of v2**: `A_LoopFileName`,
  `A_LoopFileFullPath`, `A_LoopFileExt`, `A_LoopFileDir` and
  `A_LoopFilePath`, beside `A_Index`. The tree wrote a name of its own,
  `A_LoopFile`, which v2 does not have.

The other loop kinds were measured with the archive: `Loop Parse` takes
the text and the delimiter, `Loop Read` takes the file, and `Loop Reg` is
the registry of Windows, which this box does not have -- the tree says so
and the script fails with that reason.

## 16. The reference operator, and the built-ins that write back

Measured on the binary of v2.0.19 on 2026-10-27, with probes that were run
against the real thing and read off its dialogs.

- **The marker is in the definition.** `Swap(&Left, &Right)` is a parameter
  written `&`, and the caller passes `Swap(&a, &b)`. The parameter is then
  an alias of the variable of the caller: a write inside the function is a
  write outside it. A method may have such a parameter too.
- **A reference is a value of its own kind.** `y := &x` is a valid v2 script,
  and using the reference as a value fails with "Expected a String but got a
  VarRef." A parameter that is not written `&` holds the reference and does
  not write through it.
- **`&x` is only for a variable.** A property, an item and a variable of a
  class are refused with "\"&\" requires a variable." A built-in variable, a
  function and a class are refused each with its own reason.
- **The built-ins that write back take the variable by reference.**
  `SplitPath` writes the five pieces of a path, `MouseGetPos` writes the
  place of the pointer, `StrReplace` and `RegExReplace` write the number of
  the swaps, `IsSetRef` asks whether a variable is set, and
  `VarSetStrCapacity` sets the capacity of a string. A value where a
  reference is wanted fails with the place of the parameter and the type
  of the value: "Parameter #5 of StrReplace requires a variable reference,
  but received an Integer.". Measured on the binary of v2.0.19 on
  2026-10-29: the value that was there is in the `Extra` of the failure,
  and not in the message.
- **`SplitPath` cuts the drive off the path before it cuts the name.**
  Measured on the binary of v2.0.19: the path "C:/Users/danalec/file.txt"
  gives the name "/Users/danalec/file.txt" and the directory "C:". The
  slash is not a separator of a file, and the drive is not part of the
  name.
- **The flag of the table of v2 is the place of the first parameter that is
  written back.** `CaretGetPos`, `IsSetRef` and `VarSetStrCapacity` have it
  at the first, `RegExMatch` at the third, `RegExReplace` and `RunWait` at
  the fourth, `SplitPath` at the second and `StrReplace` at the fifth.
  `MouseGetPos` is a command and carries no flag, and the four places it
  writes are its first four parameters.
- **One thing is not carried.** v2 writes into the variable of `RegExMatch`
  an object of the class `RegExMatchInfo` -- the class is in the string pool
  of the binary, beside `Map` and `Closure` -- and the tree does not carry
  that class, so the call fails with the reason. The types of the
  parameters are in a table of their own now, and section 18 is about it.

The shape of the built-ins is the shape of v2 and not of the archive:
`StrReplace` takes the case sense as its fourth parameter and writes the
number of the swaps into the fifth, and `RegExReplace` writes the number of
the swaps into its fourth and takes the limit and the place where the
search starts after it. The tree had them the way v1 had them, and a v2
script that used them was answered with something else.

## 17. How v2 is measured

The binary of v2.0.19 is at `E:\autohotkey\AutoHotkey64.exe`, and it is the
reference: every measurement in these notes came out of it.

- **A probe writes its answer to a file.** The binary forks, so the
  answer has to survive the process: the script writes to a file and the
  driver reads the file after the run.
- **A runtime error opens a dialog, and the dialog holds only the
  buttons.** The window tree of the dialog carries no text of the
  message: the message is in the picture, and it has to be read off a
  screenshot. A run that times out is a dialog and not a missing name.
- **A load-time error opens a dialog as well, and so does a load-time
  warning.** `/ErrorStdOut` catches some of the errors and not the
  others.
- **A try/catch is the way to catch a message.** The catch is written
  `catch as err` and the message is `err.What`. For the parameter error
  of a built-in it comes back empty, and the text has to be read off the
  dialog.
- **A write to the standard output that has no linefeed holds the run.**
  Measured on the binary of v2.0.19 on 2026-11-01: a probe that writes
  inside a catch must end every write with a linefeed. Without it the
  binary waits at the exit, and the run times out as if a dialog were
  there.

## 18. The type errors

Measured on the binary of v2.0.19 on 2026-10-28, with probes that were run
against the real thing and read off its dialogs.

- **There are two templates, and they are not the same.** An operation of
  the language says "Expected a Number but got a String.", and a built-in
  says "Parameter #1 of Abs requires a Number, but received a String.". The
  second one names the built-in and the place of the parameter too.
- **A built-in that casts an object uses the first template.**
  `ObjOwnProps` says "Expected an Object but got a String." and not the
  second one.
- **An empty text is an empty string.** `Abs("")` says "received an empty
  string." and not "received a String."
- **The type a parameter wants is a number, a text or an object.** The
  table in `builtins.rs` holds the built-ins whose types were measured, and
  the guard on a reference asks it: a reference where a number is wanted
  says "Parameter #1 of Abs requires a Number, but received a VarRef." A
  built-in that is not in the table takes a value of any kind, and its
  guard says "requires a value".
- **A number that is not there is not a zero.** `Abs("abc")` used to
  answer 0, and it fails now with the message of v2. The same goes for
  `Sqrt`, `Floor`, `Ceil`, `Round`, `Min`, `Max` and the trigonometry.
- **Two of the built-ins say something of their own.** `Mod` says
  "Invalid parameter(s)." when one of its arguments is not a number, and
  `Sqrt` says "Parameter #1 of Sqrt is invalid." when the number is
  negative. `Ln` and `Log` say the same of a negative number, and so do
  `ASin` and `ACos` of a number outside the unit range.
- **A text that holds a number is a number, and it keeps its kind.**
  `Abs("3")` answers the integer 3 and `Abs("3.5")` the float 3.5.

## 19. The object model

Measured on the binary of v2.0.19 on 2026-10-28, with probes that were run
against the real thing.

- **A class has a prototype, and the base of an instance is it.**
  `Alpha.Prototype` is an object of the class `Prototype`, and
  `ObjGetBase(instance)` answers it.
- **A class is one object for the whole run.** The runtime keeps the class
  values it made, so that two names of a class are the same object and the
  `is` operator can tell a class from an instance of one.
- **The `is` operator asks whether an object is of a class.** `b is Beta`
  is 1 when `b` is an instance of `Beta` or of a class that extends it,
  and 0 otherwise. Every object is an `Object`: it is the root of the
  chain. A number and a text are not objects.
- **The `is` operator wants a class.** A text on its right fails with
  "Expected a Class but got a String."
- **There is no `base` variable in v2.** This is the one that surprised the
  most: `base` inside a method of v2.0.19 is a local variable that was
  never assigned, and the runtime says "This local variable has not been
  assigned a value." A script that has a class named `Base` reads the
  class, because the names of v2 do not differ in their case. The tree does
  not carry a `base` variable, and it must not grow one.
- **The base of an object is in the property table, under a reserved
  key.** `ObjSetBase` puts it there, and `ObjOwnProps` does not name it:
  the state of an object is not a property of it.
- **The type of an object is the name of its class.** `Type(box)` is
  "Box" and `Type(Map())` is "Map", and a class itself is of the type
  "Class".
- **The `Obj` family reaches the object model.** `ObjGetBase`,
  `ObjSetBase`, `ObjOwnProps`, `ObjOwnPropCount` and `ObjHasOwnProp` are
  the tree's own. `ObjAddRef` counts the references of a COM object, and
  an object of a script has no such count: the built-in says "Parameter #1
  of ObjAddRef is invalid." The names of COM -- `ObjFromPtr`,
  `ObjFromPtrAddRef`, `ObjPtr`, `ObjPtrAddRef` and `ObjRelease` -- are
  names of Windows, and the tree says so.

## 20. The precedence of the operators

The table in `ahk::precedence` is the one of the v2 documentation, and it
was measured against the binary of v2.0.19 on 2026-10-28.

- **The power binds tighter than the sign.** `-2 ** 2` is -4 and not 4:
  the unary minus takes the whole power, the way `-(2 ** 2)` does. So the
  operand of a unary operator is parsed with the power in it, and the
  increment and the decrement -- which bind tighter than the power --
  take only the value.
- **The rest of the table is the one of the documentation.** Measured on
  the same day: `2 ** 3 ** 2` is 512 (the power is right-associative),
  `1 + 2 . 3` is "33" (the addition binds tighter than the
  concatenation), `2 * -3 ** 2` is -18, and `!1 == 1` is 0 (the `!`
  binds tighter than the comparison, while the word `not` binds looser).
- **Two values side by side are one value.** That is the implicit
  concatenation of v2, and the dot is not the only way to write it.
  Measured on the binary on 2026-10-28: `"a" 1 + 2` is "a3" and
  `1 + 2 "d"` is "3d", so the concatenation binds like the dot, and the dot
  is looser than the arithmetic.

## 21. The screen, the files and the machine

- **The size of the screen is the desktop's.** `A_ScreenWidth` and
  `A_ScreenHeight` ask the desktop, and the box answers with the geometry
  it measures from the compositor. A desktop that cannot tell says so:
  "this desktop cannot tell how big the screen is".
- **The box writes the files a script asks for.** `FileAppend` and the
  `File` class write through the desktop, and the path is the one the
  script wrote. Measured on the box on 2026-10-28: `FileAppend("hello",
  "ahk_probe.txt")` writes the file in the working directory of the run,
  and an absolute path writes where it says.
- **The machine is the desktop's.** `A_ComputerName`, `A_UserName`,
  `A_OSVersion` and the rest ask the desktop, and the box answers with the
  machine that runs the script. A desktop that cannot answer says so.

## 22. The array literal, and the loop that walks an enumeration

The two forms came on 2026-10-28, and the binary of v2.0.19 is what they
were written against.

- **The literal is the array of the `Array` built-in.** `[a, b]` is
  `Array(a, b)`, and `[]` is the array of nothing. The values go in the
  order they are written, and the places of an array count from one.
- **The bracket with a space opens the array, and the bracket without
  one is the item of the value.** Measured on the binary on 2026-10-28:
  `f [1, 2]` is a call whose argument is the array of two, and `f[1, 2]`
  is the item of the value `f` -- the item of a function is an error in
  v2, and the tree says the same. The space is the reason, and the dot
  has a rule of its own (section 39). In an expression the space does not
  matter: `arr [2]` is the second item of `arr`, in v2 and in the tree.
- **The enumerator is asked how many variables the loop wants.** v2 gives
  the `__Enum` of the object the number of the variables of the loop: it
  is 0 when the loop wants none, and one more than the number of the
  commas otherwise. The `Array` of the tree gives its values with one
  variable and the place and the value with two; the `Map` gives its
  keys with one and the key and the value with two. The map is the one
  that surprises: the enumerator of a map gives the key first, so a loop
  with one variable walks the keys.
- **A value that cannot be walked is not walked.** v2 says "Value not
  enumerable." and the tree says the same.
- **The variables go back to the values they had.** v2 restores them when
  the loop ends, and the tree does the same: a name that had no value
  before the loop has no value after it.
- **The loop has the guard rail of the other loops.** A thousand turns and
  no more, and the message is the one of the `while` loop.
- **The enumerator of the tree is a list.** The classes answer `__Enum`
  with the whole enumeration at once, and a class of the script may
  answer with a list as well. A class that enumerates one value at a time
  needs a generator, and the tree has no `yield`.

## 23. The `DllCall`, and the trampoline behind it

The tree carries the `DllCall` and it calls: a script may call a function
of a library of the machine, on Windows and on Linux.

It falls into three pieces, and the split is the rule of the tree:

- **The marshalling is pure, and it is in this crate**
  (`crates/ahk/src/dll.rs`): the names of the types, their sizes, the
  type of the answer, the convention, and the bytes of a value in the
  encoding its type asks for.
- **The call is I/O, and it is the tenth capability of the desktop**
  (`ahk::desktop::Native`): the runtime hands the desktop a `NativeCall`,
  and the desktop makes the call and answers with a `NativeResult`.
- **The box answers it** (`crates/ahk-box/src/native.rs`):
  `LoadLibraryW` and `GetProcAddress` on Windows, `dlopen` and `dlsym` on
  Linux, and a trampoline that puts the arguments where the machine wants
  them.

What v2 does with it, measured on the binary on 2026-10-28, so that the
next one does not have to measure it again:

- A library that cannot be loaded: an `Error` with "Failed to load DLL."
  and the library in `Extra`.
- A function that is not in the library: an `Error` with "Call to
  nonexistent function." and the name in `Extra`.
- A type that is not a type: a `ValueError` with "Invalid arg type.", and
  "Invalid return type." for the type of the answer.
- A number where a string is expected: a `TypeError` with "Expected a
  String but got an Integer." and the value in `Extra`.
- A string where a number is expected: a `TypeError` with "Expected a
  Number but got a String." and the value in `Extra`.
- A float as the name of the function: a `TypeError` with "Parameter #1
  invalid."
- The types are `Str`, `WStr`, `AStr`, `Int`, `Int64`, `Short`, `Char`,
  `Float`, `Double`, `Ptr` and `UPtr`, with a `U` in front of the whole
  ones and a `*` or a `P` at the end for the address of the value. The return
  type is `Int` when it is left out, and the last parameter may be
  "CDecl" or "CDecl Int" to say the convention.
- The `*` writes back: `DllCall("kernel32\QueryPerformanceCounter",
  "Int64*", &counter)` leaves the count of the clock in `counter`.
- A `Str` return reads the text at the address the function returned.

The rules of this tree, and where they differ from v2:

- **The `Str` and the `WStr` are UTF-16, and the `AStr` is UTF-8.** The
  `AStr` of v2 is the codepage of Windows, and there is no codepage in the
  tree: the text of the machine is UTF-8.
- **The `*` passes the address of a copy.** The values of the tree have no
  stable address, so the desktop allocates the block, passes its address,
  and reads the bytes the callee left there back into the variable of the
  caller.
- **The convention does not change the call of the sixty-four bits.** The
  two conventions of x64 are the same one. A call of thirty-two bits is
  the only one where they differ, and it is made by the guest of the
  thirty-two bits (section 24).
- **The `Str` with a star is the address of the text in the tree, and the
  address of the pointer to it in v2.** Measured on the binary on
  2026-10-28: v2 answers 3 for `DllCall("kernel32\lstrlenA", "Str*",
  "hello")`, and the tree answers 1. No case of the tree depends on the
  difference.

The trampoline is assembly inline, and there is no `libffi`: the shape of
the call is known when the call is made, and the cache of the cargo does
not have the crate. It was written and proved before it entered the tree,
in a prototype of its own: thirteen cases, green on Windows and fourteen
green on the box.

**The two conventions of x64 do not agree, and the tree follows each of
them.** Measured on the compiler's own assembly on 2026-10-28, on both
machines:

- **On Windows the register of an argument is the one of its place.** The
  first four arguments go in RCX, RDX, R8 and R9, and the float of the
  fourth place goes in XMM3 -- and not in XMM0, as the documentation of
  the other convention says. The float goes in the register of the
  integers of that place as well, and that is what a function that takes
  a variable number of arguments reads.
- **On Linux the register of an argument is the one of its class.** The
  integers go in RDI, RSI, RDX, RCX, R8 and R9, and the floats go in
  XMM0 to XMM7 by their own count, whatever is between them.

A function that takes a variable number of arguments is carried on Linux
and not on Windows. On Linux the number of the float registers travels in
AL, and the tree writes it there: the compiler writes `movb $1, %al` for
one float, and the tree does the same. On Windows the callee saves the
float registers in a room whose size only the callee knows, and the
trampoline cannot know that the callee takes a variable number of
arguments: the room would sit between the home space and the arguments
of the stack, and a call that is not variadic wants them the other way.

Five things about the trampoline are easy to break by accident:

- **The `asm!` of Rust does not take a name in the operand of an explicit
  register.** `inout("r9") x => _` is a syntax error; it wants
  `inout("r9") _ => x`.
- **The block has to put the `rsp` back.** `mov rsp, rbx` and `pop rbx` at
  the end, or the epilogue of the function corrupts the stack.
- **The `rsp` that is saved has to live in a preserved register.** A
  volatile one (`r10`) does not survive the call.
- **`rbx` cannot be an operand on Linux.** The LLVM reserves it there; it
  may only be used inside the text of the assembly.
- **The number of the float registers rides in the array of the integers.**
  The seventh place of that array carries it, and the assembly reads it
  into AL just before the call: the address of the array is in RAX at
  that moment, and the load of AL clears the rest of RAX, which the call
  overwrites anyway.

And the raven is not the way to call a Windows function from here. The
raven of today is a runtime that runs whole Windows programs on Linux --
C++20, CMake, the components of ReactOS, and a GPL that does not touch
this tree because it is a tool and not a part of it. Read on
2026-10-28: it loads a DLL and calls into it, but only from inside a
program of its own. There is no API of a host, and the way to have one is
a helper program inside the raven that the script talks to over its
standard input -- a program of its own, built with MinGW, running for as
long as the script needs it. The DLL would then run against the Windows
of the raven -- the synthetic one -- and not against the Windows of the
machine.

The box has Wine, and that is the lighter way to run a Windows program
there: the DLL would run against the Windows of Wine, which is a
re-implementation and not the real one. Neither of them is the way to
call a function of a library. The `DllCall` of the tree calls the `.so`
of the box itself, with the same trampoline and the convention of Linux.

## 24. The raven, and the libraries of Windows on the box

Section 23 read the raven on 2026-10-28 and said that it was not the
way to call a function of a library: it runs whole Windows programs,
and the way to have an API of a host is a helper program inside the
raven that the script talks to over its standard input. That helper is
built now, and it was proved on the box on 2026-10-28. A library of
Windows is called on the box now, and the `DllCall` of the tree answers
the libraries of both kinds.

### The raven is the upstream, and only the upstream

The raven is not ours: it is <https://github.com/mirkobrombin/raven>,
and it is built from the upstream and only from the upstream:

```sh
git clone --depth 1 https://github.com/mirkobrombin/raven.git raven-upstream
cd raven-upstream
cmake -S . -B build -DCMAKE_BUILD_TYPE=RelWithDebInfo
cmake --build build -j4
```

The program is `build/native/raven`.

**The tree is cloned on the box, and it is never copied to it.** The
build pins the SHA-256 of some of the sources of ReactOS, and the hash
is of the bytes of the file: a copy of the tree that was checked out on
a machine with CRLF line endings does not build, and it fails with a
hash that does not match and nothing else. The GPL of the raven does
not touch this tree because it is a tool and not a part of it.

### The guest is a real process

With `--execution=native` the raven runs the Windows program as a real
Linux process under ptrace, and it serves the Windows API itself. The
guest of the sixty-four bits is an x86-64 process, and the ABI of it is
the Microsoft x64 one: it is genuine, and it is the ABI that the tree
already uses on Windows.

The raven runs a guest of the width of the program it is given, and the
guest of the thirty-two bits is a real i386 process with the ABI of the
Microsoft x86. Measured on the box on 2026-10-28: the kernel32 of the
raven answered `GetTickCount` and `lstrlenA` to a guest of thirty-two
bits, and it called a library of thirty-two bits.

The kernel32 that the raven serves is its own and not the one of
Microsoft: it is the synthetic Windows of section 23.

The kernel32 of the raven is rich. Measured there on 2026-10-28, and
answered: `GetTickCount`, `GetCurrentProcessId`, `lstrlenA`,
`GetSystemTimeAsFileTime`, `GetLastError`, `GetProcAddress`,
`LoadLibraryW`, `GetModuleHandleW`, `GetStdHandle`, `ReadFile` and
`WriteFile`.

`GetProcessHeap` is the exception: it is dispatched only when the
component `raven-rtl.dll` is built, and that component needs a mingw
cross compiler. A build without it answers "Call to nonexistent
function." for a function that Windows has.

### The helper

The helper is a Windows program that the raven runs, and it is built
the way the raven builds its own programs: no C runtime, the entry
point of the PE called directly, and only the kernel32 imported. It
lives in `crates/ahk-box/helper/helper.c`.

Its build needs no mingw and no headers of the Windows: the import
library is made by `llvm-dlltool` from a definition file of five names
-- `LoadLibraryW`, `GetProcAddress`, `GetStdHandle`, `ReadFile` and
`WriteFile` -- and the program is linked by clang with lld:

```sh
llvm-dlltool -d kernel32.def -l libkernel32.a
clang --target=x86_64-w64-windows-gnu -fuse-ld=lld -O2 -nostdlib -fno-stack-protector -fno-builtin \
  -Wl,--entry,raven_entry,--no-insert-timestamp -o helper.exe helper.c -L. -lkernel32
```

The guest of the thirty-two bits is built out of the same source, with
the import library of the i386 and the assembly of the call of the
thirty-two bits:

```sh
llvm-dlltool -d kernel32.def -l libkernel32_32.a -m i386
clang --target=i686-w64-windows-gnu -fuse-ld=lld -O2 -nostdlib -fno-stack-protector -fno-builtin \
  -Wl,--entry,raven_entry,--no-insert-timestamp -o helper32.exe helper.c helper32.s -L. -lkernel32_32
```

The linker says that it resolves `__imp__LoadLibraryW@4` to
`__imp__LoadLibraryW`: the definition has no decoration, and the
thirty-two bits wants one. The call is the one the guest of the
thirty-two bits makes, and the kernel32 of the raven is a library of
Windows: it takes its arguments back.

**The register that keeps the stack of the call cannot be one of the
volatile ones.** `R11` is volatile in the Windows x64 ABI: the callee
takes it, and the stack that the trampoline had prepared is lost -- the
guest then reads outside its memory, and the raven says "native read
exceeds readable guest memory". The stack has to be kept in `RBX`,
which the callee gives back. The trampoline of
`crates/ahk-box/src/native.rs` already says this; the helper paid for
it again on 2026-10-28, and the guest read outside its memory until
the stack was kept in the register that the callee gives back.

### The thirty-two bits

The tree calls a library of thirty-two bits, and it calls it through a
second guest of the raven.

- **There are two helpers.** The one of the sixty-four bits is
  `helper.exe` and the one of the thirty-two bits is `helper32.exe`,
  and both come from `crates/ahk-box/helper/helper.c`: the compiler of
  the C picks the path of the machine, and the thirty-two bits brings
  `helper32.s` with it.
- **The box asks the sixty-four bits first.** The guest of the
  sixty-four bits does not have the library of thirty-two bits -- the
  raven skips a library of the other width -- and it answers "Failed
  to load DLL." The box then asks the guest of the thirty-two bits, and
  the answer of the library comes from there.
- **A function that is not in the library is not looked for in the
  other guest.** The library was there and the function was not, and
  the reason of v2 is the one the guest of the sixty-four bits gave.
- **The libraries of the two widths live in the same folder.** The
  raven looks for the file of a library in the folder of the program,
  and it skips the one that is of the other width: the folder of the
  helper holds the libraries of both widths, and each guest takes the
  one that is its own.
- **The width of a pointer is the width of the guest.** The tree sends
  eight bytes for a `Ptr`, and the guest of the thirty-two bits reads
  four. The address of the tree is never the address of the guest, and
  the value is the number that the script wrote.
- **The convention does not matter in the thirty-two bits.** The two
  conventions of the x86 differ in who takes the arguments back, and
  the helper puts the stack where it was after the call: the callee may
  take them back or leave them.

Measured on the box on 2026-10-28, inside the raven, with a library of
thirty-two bits of its own: the answer of a whole number, the answer of
a double, the answer of a float of four bytes, the text that comes back
as its bytes, and the value that the callee writes into the block of an
address all came right. Measured through the runner on the same day:
the same five calls answered right, the library of the sixty-four bits
was still called by the guest of the sixty-four bits, and a library that
is in neither width answered "Failed to load DLL.".

### The library of the guest is found beside the helper

The raven looks for the file of a library in the folder of the program,
and then in the system directory of the prefix. A library that is in
neither is not found, and the answer is "Failed to load DLL.". The
helper and the libraries that a script calls live in the same folder:
the helper is the program of the raven, and the folder of the program
is the first place the raven looks.

### The protocol

The protocol is one line per call, tab separated, and every value in
hexadecimal: the library, the function, the type of the answer, the
number of the arguments, and then the type and the value of every
argument. The answer is `ok` and the value and the blocks that came
back, or `error` and the reason.

The type is the name the tree spells it with, and a star at the end
says that the argument is the address of a value. The table of the
helper holds those names in lower case, and it matches them exactly.

The reasons are the messages of v2.0.19: "Failed to load DLL.",
"Call to nonexistent function.", "Invalid arg type." and "Invalid
return type.".

What the helper proved on the box, on 2026-10-28, inside the raven:

- `GetTickCount` and `GetCurrentProcessId` answer their number.
- `lstrlenA` answers 5 for a text of five characters that went out by
  its address.
- `GetSystemTimeAsFileTime` writes the time into the block of an
  address, and the block comes back.
- A float of eight bytes comes back in the float register, and the bits
  are right; a float of four bytes likewise.
- A text comes back as the bytes of the text.
- A library that does not exist answers "Failed to load DLL.", and a
  function that does not exist answers "Call to nonexistent function.".

### The routing on the box

A library whose name carries a slash in it, or ".so" in it, is a
library of this machine, and the direct path of section 23 answers it.
Every other name is a library of Windows, and the raven answers it: the
backslash of a path of Windows is the one that sends it there.

**The rule is a rule of the box.** On Windows the machine is the
Windows, and every library is called by the direct path: the raven is
not there, and the name of the library does not decide anything.

Inside the raven there are two guests, and the box asks them in this
order: the guest of the sixty-four bits first, and the guest of the
thirty-two bits when the first does not have the library.

The raven is named by the environment: `AHK_RAVEN` is its program,
`AHK_RAVEN_HELPER` is the guest of the sixty-four bits, and
`AHK_RAVEN_HELPER32` is the guest of the thirty-two bits. A box that
does not have the first two says so, and it does not answer with a
wrong answer. The guest of the thirty-two bits is not needed: a box
that does not have it calls the libraries of the sixty-four bits and no
more, and a library of thirty-two bits answers "Failed to load DLL.".

### The raven is a long-lived process

It starts with the first library of Windows that a script asks for, and
it lives until the desktop is dropped. Its standard input and its
standard output are the pipes of the host. Its standard error goes
nowhere: the reason of a failure comes back in the protocol. The
timeout of the guest is a day.

**The raven stops with the runner, even when the runner is killed.** The
pipe of the standard input of the raven is held by the runner, and the
kernel closes it when the runner dies: the guest reads the end of it and
stops, and the raven stops with it. Measured on the box on 2026-10-28:
the raven was there while the script ran, and it was gone three seconds
after the runner was killed with SIGKILL. The emergency stop of section 8
does not have to know about the raven.

### The limits

The call is the one of the Microsoft x64, and the limits of it are the
limits of section 23: a call that takes a variable number of arguments
cannot be made, because the callee saves the float registers in a space
whose size only the callee knows.

The call of the thirty-two bits is the one of the Microsoft x86, and it
has the limit of the others: the number of the float registers would
have to ride in AL, and the helper does not write it there.

The `Str*` of the tree passes the address of the bytes of the text, and
v2 passes the address of the pointer to it: the difference is measured
in section 23, and it is the same on the two paths.

## 25. The date, the files, the settings and the hotkeys

Four blocks of names answered with a reason where they should answer with
a value. They answer now, and each one is a module of its own.

### The date and the time

- **The date comes from the host, through the `Clock` trait.** The trait
  gained `wall_clock`: it answers with the local time of the machine and
  with the same moment in UTC, and it answers with nothing when the host
  does not know the date. The names of the date answer with the reason
  then: "the clock of this runtime does not know the date of the machine."
- **The zone of the machine is not in the standard library.** The host
  reads the file of the zone (`/etc/localtime`) or the `TZ` of the
  environment, and says whether the machine knows it. A machine that does
  not know has UTC as its local time, and the runtime says so.
- **The arithmetic is in the language crate, and it is pure.** The crate
  builds without the standard library, and the date is not an exception:
  a crate that has no `std` has no `time` either.

Measured on the binary of v2.0.19 on 2026-10-28: `DateAdd` takes the
date, the amount and the unit, and **the unit comes last**
(`DateAdd("20260101", 1, "d")` is the second of January); the units are
`d`, `h`, `m` and `s`, and there are no years and no months; the date is
fourteen digits and has no milliseconds; `A_Now` is the local time and
`A_NowUTC` is the UTC one; `A_WDay` counts the Sunday as one; `A_YWeek`
is `YYYYWW`.

On the lab box on 2026-10-29 the date answered `20261029000412`, and the
format of v2 answered `2026-10-29 00:04:12`.

### The files of the machine

- **The operations on the files are the `Files` capability.** The copy,
  the move, the attributes, the times, the directories and the ini files.
- **An ini is an ini of Windows.** `[section]`, `key=value`, and `;` for a
  comment.
- **The two that open a dialogue are not carried.** `DirSelect` and
  `FileSelect` ask the script to choose a file, and a box without windows
  has no way to ask.

Measured on the binary of v2.0.19 on 2026-10-28: the names that *set*
something take the value first -- `FileSetTime "20000101000000", file, "M"`
-- and the ones that *read* it take the file first; `FileGetTime` answers
with fourteen digits; `FileExist` answers with the **attributes** of the
file and not with a number: `A` for a file, `D` for a folder, and the
empty text when the file is not there; `IniRead` without a default fails
with "The requested key, section or file was not found."

The `FileEncoding` of the tree keeps the name the way v2 keeps it:
`utf-8` becomes `UTF-8`, and the suffix `-RAW` is kept. The box has no
code pages, so a name of a code page -- `CP1252`, the one v2 accepts and
resolves -- is refused with the message v2 gives for a name it does not
know. The bytes of a file are UTF-16 when the encoding says so, and
UTF-8 otherwise: the default of v2 is the code page of the machine, and
the machine of the box has none.

### The settings of the pointer and of the keyboard

- **The state belongs to the script, and not to the machine.** The mode of
  the coordinates, the delays, the method of the send, the speed of the
  pointer and the mode of the caps lock are the script's own, and the
  module of the settings keeps them. The state is in the module and not
  in the runtime: the runtime has no field for it, and the crate runs
  without the standard library, so there is no mutex of the standard
  library either.
- **The modes of the coordinates that need windows answer with the
  reason.** The mouse and the pixels are the two that a box without
  windows has. v2 answers "Client" for the three others, and the tree
  says that it cannot do them.
- **The names of the keys are in `keys.rs`.** `GetKeySC` is the code of
  the Linux input event and `GetKeyVK` is the virtual code of Windows.

Measured on the binary of v2.0.19 on 2026-10-28: the speed of the
pointer is from 0 to 100 and its default is 2; `A_KeyDelay` is 10;
`A_SendMode` is `Input`; `A_MenuMaskKey` is `vk11sc01D`; `A_FileEncoding`
is `CP0`.

### The hotkeys

- **The runtime holds the registry and the machine holds the watcher.**
  The script says which function a hotkey runs; the machine says which
  key was pressed. The runtime asks between the statements of the script,
  and only at the top level: a hotkey runs with the scope of the script
  and not with the one of a function.
- **The box reads the physical keyboard.** The keyboard of the box
  *writes* (the uinput); the hotkeys need the keyboard that *reads*, and
  that is the physical one. The virtual devices are skipped: a hotkey
  that fires on what the script writes is a hotkey in a loop.
- **The device may be named.** `AHK_HOTKEY_DEVICE` says which one to
  read, and it is how the hotkeys are proved on the box without a person
  at the keyboard. The variable may hold the path of the device or its
  name, and the device is opened when the first events are wanted: the
  keyboard of the box is made when the script types for the first time,
  and a watcher that wanted a device that is not there yet would say
  that the hotkeys cannot be watched.

Measured on the binary of v2.0.19 on 2026-10-28: the callback receives
the name of the hotkey; the action of a hotkey has to be the object of
the function -- `Hotkey "a", "b"` is "Parameter #2 of Hotkey is
invalid."; the name of a hotstring is written between two of the same
character and it is checked before the action -- `Hotstring "btw", "b"`
is "Parameter #1 of Hotstring is invalid."; `HotIf` only takes the object
of a function.

The action of a hotstring may also be a text -- v2 takes the name of a
label of the script, and the tree has no labels: the text is the name of
a function of the script, and a hotstring of a function that the script
does not have is a hotstring of nothing.

## 28. `NumGet` and `NumPut` read and write the bytes of a buffer

The two names answer with a value now, on top of the `Buffer` class that
the tree already had.

- **The source of a number is a buffer, and not an address.** v2 accepts
  a memory address, and the tree does not read the memory of an address:
  the bytes of a buffer live inside the runtime, and an address fails
  with the reason. This is the same divergence the buffer itself already
  has, and it is the safe one.
- **The types are the ones of v2** -- `UInt`, `Int`, `Int64`, `Short`,
  `UShort`, `Char`, `UChar`, `Float`, `Double`, `Ptr` and `UPtr` -- and
  they are read from the table of the native calls, so that the width of

## 31. The machine is a capability of its own

## 32. The facts of the script

Four names of v2 refused with the reason that the runtime does not know the

## 33. The spelling of the variables is the spelling of the dialect

## 34. The shape of the runtime, and the reason of each name of it

Fourteen names of v2 refused with one reason -- "this runtime is one script
that ends when it ends, and it cannot do that." -- and that reason hid
fourteen different things. Each of them refuses now with the reason of the
thing it wants, and the one that the runtime can do is carried.

- **`OnExit` is carried.** The script asks for a function of itself, and the
  runtime calls it when the script ends: the end of the last statement, the
  code it asked to stop with, or the error that stopped it. The callback is
  a function object, and the shape of it, the order of the callbacks and
  the answers of a callback are in section 36.
- **The thread of the runtime is one.** `Critical` and `Thread` say that the
  runtime runs one script in one thread, and that it cannot make it critical
  or start another.
- **The script cannot wait, cannot stay, cannot run again and cannot stop.**
  `Pause`, `Persistent`, `Reload` and `Suspend` each say what they want.
- **The lists and the question are windows of v2.** `ListLines`, `ListVars`
  and `InputBox` are windows, and this runtime has no window to show them
  in.
- **The download, the picture and the search are the desktop's.** `Download`,
  `LoadPicture` and `ImageSearch` say that this desktop does not reach the
  network and does not read the images of the machine.
- **`OnError` is carried too.** It is the handler of the failures that no
  `try` catches, and section 36 says what it receives and what it answers.

And a function of the exit that fails does not pass silently: the run fails
with the failure of the function, and when the script had already failed the
failure of the function is a note of the report.

Measured on the box on 2026-10-29: a script with `OnExit Bye` and a function
`Bye` that writes "bye" ended with "the script ends" and then "bye", and
`Critical` refused with the reason of its own thing. The surface answers 508
names with a value and refuses 217.

## 35. The error handling of the dialect

The tree did not have `try`, `catch`, `finally` or `throw`: a script of v2
that used them did not even parse. They are carried now, the way v2.0.19
carries them, and the failure of the runtime has two kinds -- the error,
which a catch takes, and the value that `throw` throws, which only a catch
of `Any` takes.

- **`try { }` guards the statements of its block** against the errors of
  the runtime and against the values that `throw` throws.
- **A catch names the class it takes.** `catch { }` takes the class
  `Error`, which is the class of the errors of the runtime; `catch Any { }`
  takes everything; `catch <Class> { }` takes the objects of that class and
  of the classes that extend it. A class that the tree does not know fails
  with the reason.
- **`catch as e { }` binds the value.** An error of the runtime is an object
  of the class `error`, and it has the properties of v2: `What`, `Message`,
  `Extra`, `File` and `Line`.
- **`else { }` runs when nothing was thrown, and `finally { }` always
  runs.** The value is thrown again after the `finally`.
- **`throw value` throws a value, and `throw` alone throws again what the
  catch took.** A value that no catch took is the error of the run:
  "Unhandled exception.\n     Specifically: the text that was thrown".

Measured on the binary of v2.0.19 on 2026-10-29: a `try` with a `catch`
takes an error of the runtime, and a `throw` of a text is not taken by a
catch without a class -- the binary answers "Unhandled exception.
Specifically: the error of the script", and the stack of the error shows the
`Catch` under the `Throw`. A catch of `Any` takes it. The documentation of
v2 says the same: "If no classes are specified, the default is Error", and
a text is not an `Error`.

And a name that is not a word of the dialect is a word of nothing: `gosub`
and `var` are not in v2, and the binary reads them as variables of the
script: a variable that has no value is a variable that has no value
(section 71).

## 36. The handlers of the runtime

`OnExit` and `OnError` register a function of the script, and the tree calls
it the way v2.0.19 calls it. Everything in this section was measured on the
binary of v2.0.19 on 2026-10-29 and 2026-10-30.

- **The callback is a function object.** A text is refused with the wording
  of v2: "Parameter #1 of OnExit requires an Object, but received a String.
  Specifically: Bye".
- **A value that cannot be called is refused too.** v2 calls the value, and a
  value that is not callable has no method named "Call": "This value of type
  "Object" has no method named "Call"."
- **The prototype has to take the two parameters of the callback**: the
  reason and the code for the exit, the value and the mode for the error. A
  prototype that does not fit is refused with "Invalid callback function.".
  A parameter that takes the rest fits: it takes what is left.
- **The order is a number that is cut to a whole number, and it is 1, -1 or
  0.** One calls the callback after the ones that are registered, minus one
  before them, and zero does not call it at all -- it removes it. Anything
  else is refused with "Parameter #2 of OnExit is invalid.\n     Specifically: 5",
  and a text that is not a number with "Parameter #2 of OnExit requires a
  Number, but received a String".
- **The callback of the exit takes the reason and the code.** The reasons the
  tree carries are "Exit" and "Error"; the reasons of Windows are not
  carried.
- **The callback of the error takes the value that was thrown and the mode.**
  The mode is "Return" for a failure of the runtime, "Exit" for a value that
  the script threw, and "ExitApp" for the timeout of the tree.
- **The answer of the callback of the error is what v2 says it is.** Zero
  lets the failure go on, one hides it, and minus one hides it and lets the
  thread continue where the failure happened. A callback that answered stops
  the ones that come after it.
- **The callback of the exit that answers a number that is not zero keeps the
  script alive**, and the callbacks that come after it are not called. This
  runtime has no way to keep a script alive, so the run ends and the note
  says so; the code the script asked for is not the code of the run.
- **The functions of the error are called where the failure happened**,
  before the stack unwinds, and they are not called while the body of a
  `try` runs: the catch of the script takes the failure first.

Two things are not carried yet. The tree has no reference to a method of the
script, so a method and a bound function are not callbacks the tree can take
(the `Bind` of the class `Func` refuses too). And the error object of the
runtime has an empty `What` and an empty `Extra`: the tree's error does not
name the built-in that failed and does not carry the value it was given.

## 37. The names of the script do not know their case

The tree kept the variables as they were written, and the dialect does not
know the case of the names: `x` and `X` are the same variable.

- **The key of a variable is in lower case.** `the_key_of` in `runtime.rs` is
  the one that writes it, and the lookup, the assignment, the restore of a
  loop and the reference of a variable all go through it.
- **The names of the functions were already in lower case**, and the
  parameters of a function and of a method are like them now.
- **The report carries the names in lower case**, because the report is the
  table of the variables of the script.

Measured on the binary of v2.0.19 on 2026-10-30: `x := 1` and then `X`
answers 1, `X := 2` writes the variable `x`, a parameter read in another
case is the same parameter, and a global declared in another case is the
same global.

## 38. The declarations of v2: `global` and `local`

`global` and `local` are declarations of v2, and the tree carries them. The
words are keywords of the dialect: a script cannot use them as names.

- **A function assigns a local by default, and the tree already did.** The
  reading of a name that was never assigned in the function falls back to
  the scope of the script, and that is the rule of v2: "any variable
  reference in an assume-local function may resolve to a global variable if
  it is only read".
- **A declaration names where the name lives.** `global g` makes the
  assignments to `g` inside the function write the scope of the script, and
  `local l` makes the name local. The declaration may name several
  variables -- `global a, b := 1` gives the value to `b` -- and it may
  give a value: `global g := 1` writes the global right away.
- **The names are read when the script is read.** v2 says so: "the words
  local, global, and static are processed immediately when the script
  launches", so a declaration inside a block takes effect for the whole
  function. Only the value waits for the statement that carries it. The
  parser reads the names of a body -- `the_declarations_of_a_body` -- and
  the frame of the function carries them.
- **A bare `global` is the mode of the function.** On the first line of a
  body, every name the function does not name lives in the scope of the
  script. Anywhere else it is refused, and so is a bare `local`, which is
  never a thing.
- **The refusals are the wording of v2.** "Unexpected declaration.\n
  Specifically: local l" for a `local` outside a function, "Unexpected
  declaration.\n     Specifically: global" for a bare `global` that is not
  the mode, and "This global variable declaration conflicts with an
  existing parameter.\n     Specifically: p" for a declaration of a
  parameter. They are refusals of the grammar, so they are load errors: the
  runner answers 2.

Measured on the binary of v2.0.19 on 2026-10-30.

What is not carried yet: `static`, which is the third declaration of v2 and
keeps the value of a name between the calls of a function, and the `super`
of a class, which calls the method of the base.

## 39. The dot of v2 tells a member from a concatenation

The tree had this the other way round: it said that the space *before* the
dot tells a member from a concatenation. Measured on the binary of v2.0.19 on
2026-10-30, it is the space that comes *after* the dot.

- **`o.x` reaches into the value, and `o .x` reaches into it too.** The space
  that comes before the dot does not matter: `o .x := 1` writes the property
  `x` of the object `o`, and `1 .2` asks the integer `1` for its property
  `2`.
- **`o. x` is neither.** The dot has no space before it and a space after
  it, and v2 refuses the line: "This line does not contain a recognized
  action.\n     Specifically: o. x := 1". In an expression it is a load error too:
  "Syntax error.\n     Specifically: . x".
- **`o . x` joins two values.** The concatenation wants a space on both
  sides, and it is looser than the arithmetic.

So the member is the dot with no space after it, and the concatenation is the
dot with a space on both sides. The bracket keeps its own rule: in an
expression the space does not matter (`arr [2]` is the second item of `arr`),
and as the left side of an assignment the bracket without a space is the item
(`o["a"] := 1`), while the bracket with a space is not ("Invalid assignment.
Specifically: := 1)").

## 40. The `super` of v2 is the base of the class where the method was defined

`super` is a keyword of v2, and the tree carries it. The documentation says
what it is: "the keyword super can be used in place of this to access the
superclass versions of methods or properties which are overridden in a
derived class", and "super.Method() always invokes the base of the class or
prototype object associated with the current method's original definition,
even if this is derived from a subclass of that class or some other class
entirely".

- **The base is the one of the class that defined the method.** A method that
  `Derived` inherits asks the base of the class that wrote it, and not the
  base of the class of the object. The frame of the runtime carries the
  class that defined the method that runs (`current_classes`), and the base
  is the one after it in the chain of the classes.
- **The base gets the same `this`.** `super.m()` is `Base.m(this)`.
- **The three forms.** `super.m()` calls the method of the base, `super.value`
  reads the property through the getter of the base, and `super["x"]` asks
  the base for the item. The documentation adds the fourth: `super()` is
  `super.call()`, and the tree carries it too.
- **A property is read through the getter of the base.** The instance
  variable of the base is not read: measured on the binary of v2.0.19 on
  2026-10-30, `super.value` refuses when the base only has
  `this.value := ...`, and answers when the base has a getter. The tree has
  no getter of its own, so the `__Get` of the base is what answers.
- **The refusals are the wording of v2.** Outside a class the keyword is
  refused when the script is read: '"Super" is valid only inside a class.
  Specifically: super.m()'. The text of it is the source of the expression as
  it stands -- `super.m(1, 2)` keeps the space after the comma, and
  `super["x"]` keeps the quotes -- and a member that is not called is
  written with the parentheses of a call, because that is what it is.
  The keyword alone is refused as well: "Syntax error.\n     Specifically: super".
- **The refusals of the base name the class of the value.** 'This value of
  type "Derived" has no method named "n".', and 'This value of type
  "Derived" has no property named "value".'

Measured on the binary of v2.0.19 on 2026-10-30.

## 41. The `__Init` of v2 runs when an instance is made

The tree never called the `__Init` of a class: an instance was made with its
variables and its `__New`, and the `__Init` was a method that nothing called.
Measured on the binary of v2.0.19 on 2026-10-30, and against the
documentation of v2, which says that the variables of a class are "evaluated
each time a new instance of the class is created with ClassName(), after all
base-class declarations are evaluated but before __New is called".

- **The `__Init` runs before the `__New`.** The `__New` is the constructor of
  the instance and it takes the arguments of the constructor; the `__Init`
  takes none.
- **The most derived `__Init` is the one that runs.** It is the explicit one
  of the class, or the automatic one that carries the variables of the class.
  The automatic one calls the `__Init` of the base before it assigns the
  variables, and the explicit one calls nothing at all: the variables of the
  base are **not** assigned when the derived has an `__Init` of its own.
- **Every class has an `__Init`.** So `super.__Init()` never fails for want
  of a method: it runs the one of the base, the explicit one or the
  automatic one. And the instance has it too: `d.__Init()` runs it again.
- **A class may not have an `__Init` of its own and variables of its own.**
  v2 makes the `__Init` that carries the variables, and the two cannot both
  be there: "Duplicate declaration.\n     Specifically:
  Thing.Prototype.__Init". It is a refusal of the grammar, so it is a load
  error. The variables that come *after* the `__Init` are another thing:
  v2 takes them, and the tree takes them too (section 85).

- **The class of v2 is initialised when it is first referenced.** The tree
  does that: the statement that defines the class is a use, the static
  variables of the class are assigned then, and the static `__New` runs
  then -- once, and the one of the base of it as well. The class that is
  never used is initialised all the same, because the statement that
  defines it is a use.
- **The `__New` of an instance is the constructor of it, and the `__Init`
  is the one of v1.** Both run when the instance is made, and the `__Init`
  of v1 runs before the `__New`.

The comparison of the tree with the binary is in
`egm-review/compare_class_init.py` (15 cases, none of them different) and
in `egm-review/compare_class_first_use.py` (eight cases, none of them
different). The probes that measured the rules are in
`egm-review/probe_class_init.py` and `egm-review/probe_class_new.py`.

## 42. The numbers of v2 are the numbers of v2

The tree read the decimals and nothing else: `0xE9` was the number `0` and
the name `xE9`, and `1e3` was the number `1` and the name `e3`. Measured on
the binary of v2.0.19 on 2026-10-30, and against the documentation of v2,
which says that "numbers are considered to be floating point if they contain
a decimal point or scientific notation; otherwise, they are integers", and
that "integers may be written in either hexadecimal or decimal format".

- **The hex is a number of the base of sixteen.** `0xE9` is 233, `0xDeadBeef`
  is 3735928559, and the number of the machine wraps: `0xFFFFFFFFFFFFFFFF` is
  `-1`. The hex is written in the expressions and outside them: `Sleep 0xFF`
  is `Sleep 255`.
- **The exponent is a number too.** `1e3` is 1000, `1e-3` is 0.001, `1E3` is
  1000 and `1.5e2` is 150.
- **The shape of the literal is the shape of the value.** A number with a

- **The questions ask the class of the value.** `HasProp([1, 2], "Length")` is
  one and `HasMethod([1, 2], "Push")` is one: the array answers about its own
  properties and methods.
- **A class is not an instance of itself.** `HasProp(Map, "Count")` is zero
  and `HasMethod(Array, "Push")` is zero: the properties and the methods of
  the instances are not the ones of the class.

One gap is left open. The names that the tree does not carry answer with
the reason of the machine, where v2 refuses the reference with the kind it
wanted: the `StrPut` and the `ComObjConnect` are the ones. The other one,
the `HasMethod` of a class with no name, was closed by section 62.

Forty-eight of the seventy-one built-ins that take one argument are the same
in the tree and in the dialect when they are called with a reference, and
thirty-two of the thirty-four questions about a value are the same too. The
ones that are not are the names that the tree does not carry, and the
questions about a class with no name. Section 68 closed the first ones.

## 59. The enumeration of v2 is an Enumerator, and a catch takes every error

Measured on the binary of v2.0.19 on 2026-10-31: the tree handed out the
enumeration of a value as a plain list, and v2 hands out an object of the
class `Enumerator`. `Type([1, 2].__Enum())` is "Enumerator", and so is the
`OwnProps` of an object and the `ObjOwnProps` of it.

- **The enumeration is a class type of the runtime.** The `Enumerator` is a
  function of its own kind: it derives from `Func`, it carries the values of
  a function -- the name of it is empty, it wants no parameters, and it is
  built in -- and its `Call` is the turn of the enumeration. It is not made
  by a call: `Enumerator()` answers "Invalid base.", the way a `Func` does.
- **The `Call` of it hands out the next turn.** It answers one while there is
  something left and zero when there is nothing left. The first variable of
  the caller gets the key and the second the value under it.
- **The one of the two that it gives alone is the dialect's.** A caller that
  gives one variable gets the one of the two that the enumerator gives
  alone: the enumerator of an array gives the value, and the enumerator of a
  map gives the key. Measured: the enumerator of `[10, 20]` writes 10, and
  the enumerator of a map with the key "k" writes "k".
- **The own properties of an object are an enumerator too.** It gives the
  name when the caller wants one value, and the name and the value under it
  when the caller wants two.
- **The enumerator is not indexed.** `e[1]` answers "This value of type
  "Enumerator" has no property named "__Item"."
- **The enumerator has no enumeration of its own.** `e.__Enum()` answers
  "This value of type "Enumerator" has no method named "__Enum"."
- **The loop walks the enumerator.** The number of the variables of the loop
  is what says how many values a turn has, and not the enumerator: the
  enumerator of an array built with one variable and the one built with two
  hand out the same turns.

One gap was found on the way. The `catch` of the tree without a class took
only the failures whose class was exactly `Error`, and every other failure of
the runtime escaped it: `catch as e` takes a division by zero in v2, and it
did not in the tree. The catch without a class takes every error of the
runtime now, because every one of them is an `Error`.

A class of the script may still hand out a list instead of an enumerator, and
the tree walks that one the way it always did. v2 does not: the enumeration of
a class has to be an enumerator there. The gap is left open.


## 60. The split of a text, the descriptor of a property and the order of the files

Measured on the binary of v2.0.19 on 2026-10-31: the places where the tree said
something else than the dialect. Every one of them is measured now, and the tree
says what the binary says.

- **The delimiters of the `StrSplit` are literals, and not sets of
  characters.** `StrSplit("a,b;c", ",")` is one piece, and
  `StrSplit("a.b-c", [".", "-"])` is three: the delimiters of an array are
  tried in the order they were given, and the first one that is there wins. A
  delimiter that is empty cuts between every two characters, and
  `StrSplit("abc")` is three pieces. A delimiter that is neither a text nor an
  array is refused: "Parameter #2 of StrSplit is invalid.".
- **The characters to leave out trim the edges of every piece.**
  `StrSplit("a,b,c", ",", "b")` is `a`, an empty text and `c`. With a
  delimiter that is empty they are not in the answer at all:
  `StrSplit("abc", "", "b")` is `a` and `c`.
- **The last parameter of the `StrSplit` is the number of the cuts.**
  `StrSplit("a,b,c", ",", "", 2)` is `a` and `b,c`: the rest of the text is
  the last piece. Zero is an answer with no piece, and a negative number is
  no limit at all.
- **The answer of the `StrSplit` is an array.**
- **A property is written with a descriptor.** The `DefineProp` takes an
  object with a `Value`, a `Get`, a `Set` or a `Call` in it, and nothing else:
  "Parameter #2 of Object.Prototype.DefineProp is invalid.". A value and an
  accessor together are refused the same way. The read of a property with a
  `Get` calls it, and the object is the first parameter of it; the write
  calls the `Set`, and the object and the value are its two parameters; a
  property with a `Get` and nothing else is read-only, and the write says
  "Property is read-only.". The `DefineProp` answers the object, the
  `GetOwnPropDesc` answers an object with the members of the descriptor, and
  the `DeleteProp` answers the value that was taken away.
- **The braces that are not closed are named in the words of v2.** The class
  that is not closed says "Missing \"}\"\n     Specifically: Foo", and the
  block that is not closed says "Missing \"}\" and nothing else: v2 never
  names the line of a block that is not closed.
- **The switch says what it wants.** A statement that is not a case is
  refused with "Expected Case/Default.", a case without its colon says
  "Missing \":\"\n     Specifically: case 1", and the switch that is not
  closed says "Missing \"}\"".
- **The member of a class that is not a definition is refused with the line
  that says it.** "Not a valid method, class or property definition.\n
  Specifically: x .= \"y\"". A member that is a name and nothing else is a
  line with no action in it: "This line does not contain a recognized
  action.\n     Specifically: x".
- **The concat of a variable that has no value is the concat of an empty
  text.** `s .= "x"` on a variable that has no value is `x`, and the write
  makes the variable. The other operators want a value that is there, and
  `n += 2` is "This global variable has not been assigned a value.".
- **The compound operators read the property before they write it.** A
  property that is not there is an error that names it: `o.x .= "y"` is
  "This value of type \"Object\" has no property named \"x\".", and the
  setter of the object is not called.
- **The pattern of a loop over the files is a path.** The folder of it is
  where the files are and the rest of it is the name of them: `Loop Files,
  "sub\*.txt"` is the files of the folder `sub`.
- **The case of the pattern does not count.** `*.TXT` is every file that ends
  with `.txt`.
- **The files of a folder come in the order of the name with the case taken
  away.** The names are compared byte-wise, and the order of a directory is
  not the order of its name: the files of a folder of NTFS come in the order
  of the index of the folder, and `10.txt` comes before `2.txt`.

Two things are apart, and they stay apart. The relative pattern of v2 is
resolved against the working directory, and the working directory of v2 is the
folder of the script; the script of the runner has no file, so the tree
resolves it against the folder where the run began. And a loop over a folder
that is not there hangs v2, where the tree fails with the reason.


## 61. The name of a class is a name of the script, and a name is declared once

Measured on the binary of v2.0.19 on 2026-10-31: the tree took the name of a
class for a name that a variable may have, and it took a name that is declared
twice. v2 takes neither, and it says so at the load.

- **The name of a class is a name of the script, and it may not be the output
  variable of an assignment.** The refusal is at the load, and it is the plain
  assignment that says "This Class cannot be used as an output variable.\n
  Specifically: Foo". The compound assignments say that the class cannot be
  assigned a value: "This Class cannot be assigned a value.\n     Specifically:
  Foo". The case of the name does not count: `foo` is the name of the class
  `Foo`.
- **The classes of the runtime are names of the script too.** `Map := 5` is
  refused the same way, and so is `gui := Gui()` and `menu := Menu()`.
- **A name may be declared only once.** A class that is named like a function
  is refused with "This class declaration conflicts with an existing Func.\n
  Specifically: f", a function that is named like a class with "This
  function declaration conflicts with an existing Class.\n     Specifically:
  f", and the two declarations of the same kind with the words of their own
  kind: "This class declaration conflicts with an existing Class.\n
  Specifically: f" and "This function declaration conflicts with an existing
  Func.\n     Specifically: f".
- **A function that is written inside another one is not a name of the
  script.** Two functions with the same name may live in two functions, and
  the name of a nested one does not conflict with the name of a function of
  the top level.
- **In a function, a local may not hold the class of its own name.** `foo :=
  Foo()` is refused, and so is `foo := Foo`, and the words are the words of a
  local that has no value: "This local variable has not been assigned a
  value. A global declaration inside the function may be required." A local
  that is declared says the same words without the hint, and a local with
  another name takes the instance without a word.
- **A local that is declared is the local, and not the global.** Measured:
  `local g` and a global `g` are two names, and the function reads the local,
  which has no value until something writes it: "This local variable has not
  been assigned a value." A name that the function does not declare is the
  global one, and the tree read the global where v2 reads the local.

Three cases of the tree used a name that v2 refuses, and they were renamed:
the object of the case of `HasProp`, the window of the cases of the `Gui` and
the menu of the cases of the `Menu`. The dialect is the one that decides what
a case may write.


## 62. The base of an object is an object, and the methods of the base object are inherited

Measured on the binary of v2.0.19 on 2026-10-31: the tree asked for the base of
an object with a name, and it did not see the methods that every object
inherits. v2 asks for another object, and it counts the methods of the base
object.

- **The base of an object is another object.** The second parameter of the
  `HasBase` is an object, and a name is refused with the reason: "Expected an
  object but got a String." The refusal comes before the question of the
  object itself: `HasBase(5, "Object")` is the refusal of the name.
- **The question is whether the base of the object is the other object.** The
  chain of the bases is walked: the base of an object is the prototype of its
  class, and the base of a prototype is the prototype of the class that the
  class extends. `HasBase(m, Map.Prototype)` is one, and
  `HasBase(m, Object.Prototype)` is one as well, and
  `HasBase(m, Array.Prototype)` is zero.
- **A class is not an instance of itself, and its chain begins at the base of
  it.** `HasBase(Map, Map.Prototype)` is zero and `HasBase(Map,
  Object.Prototype)` is one. A value that is not an object has no base:
  `HasBase(5, Object.Prototype)` is zero and not a failure.
- **The methods of the base object are the methods of every object.** The
  tree answered zero for `HasMethod(o, "OwnProps")`, and v2 answers one: the
  methods of the base object are inherited.
- **The question with no name asks whether the value is a class.** A class has
  the methods of the base object, and an instance has the methods of its
  class: `HasMethod(Map)` is one, and `HasMethod(Map())` and `HasMethod({})`
  are zero.
- **A class does not have the methods of the class it is, and the prototype
  of a class has them.** `HasMethod(Map, "Get")` is zero, and
  `HasMethod(Map.Prototype, "Get")` is one.

Three cases of the tree asked for the base with a name, and they were
rewritten with the prototype of the class: the object of the case of
`HasProp`, the buffer of the case of its methods and the file of the case of
its methods. The dialect is the one that decides what a case may write.


## 63. The read of a file is the text of it, and the options of a file are the ones of v2

Measured on the binary of v2.0.19 on 2026-10-31: the tree answered the read
of a file with an array of its lines, and it refused the options that v2
takes. v2 answers with the text of the file, and the second parameter of the
read and the third one of the write are the options.

- **The answer of the read is the text of the file.** `FileRead("a.txt")`
  answers a text and not an array of lines, and the line endings of the file
  are the ones it has.
- **The options of a file are a text.** They are separated by a space or a
  tab, and each one of them is a word: the encoding of the file, `RAW`,
  `m<n>` and a linefeed. The last one of a kind is the one that counts.
- **The linefeed of the options is a character of its own.** It is the
  character 0x0A, and not the text of a backtick and an n: that text is an
  option that v2 does not know.
- **The size of the read is a number of bytes.** `m5000` and `m0x1388` are
  the same size, and a `m` with no number is zero bytes. The size is an
  option of a read and not of a write: v2 refuses it in a write with
  "Invalid option.".
- **The raw answer is a buffer.** `FileRead("a.txt", "RAW")` answers a
  buffer of the bytes of the file, and the mark of the file is one of them.
- **The mark of the file decides the encoding of it.** A file that begins
  with the mark of UTF-8 or of UTF-16 is read in that encoding, whatever
  the option of the script says, and the mark is not in the text.
- **The linefeed of a read takes the carriage return away, and the linefeed
  of a write puts one there.** The read of a file of Windows with the
  option of the linefeed is the file of Unix.
- **The raw write is the text of v2.** The text of a script is UTF-16, and
  a raw write writes the units of it, without a mark.
- **The mark of the encoding is written when the file is made.** A file
  that is already there keeps what it has, and a new file with the option
  of UTF-8 begins with the mark of UTF-8.
- **The default of the encoding is the code page of the machine.** The tree
  carries the code page of the machine where the dialect was measured, and
  a letter that is not of it is one byte.
- **An option that v2 does not know is refused with the words of v2.**
  "Invalid option.", of the class `ValueError`, with the name of the
  command in the `What` and the option in the `Extra`.
- **The failure of the machine is the code of the system in front of what
  it says.** "(2) The system cannot find the file specified." for a file
  that is not there, "(3) The system cannot find the path specified." for a
  folder that is not there, and "(5) Access is denied." for a folder that is
  read.
- **The fill of a buffer is the byte of the number.** v2 does not refuse a
  number that is not a byte: the byte of it is the fill.
- **The names of a folder come in the order of the name with the case taken
  away.** The pattern of `FileExist` answers with the first of them, and it
  is the order of the `Loop Files`.

The tree keeps the bytes of the file in the machine and the text of it in
the dialect: the desktop answers with the bytes of a file, and the module of
the files reads them in the encoding that the script asked for.

## 72. The label of a script and the jump of a Goto

Measured on the binary of v2.0.19 on 2026-10-31: the `Goto` is a word of
the language and not a name of the built-in table -- it stands with `Try`,
`Catch`, `Throw` and `Switch` in the pool of the words of the binary -- and
that is why the table of the surface does not carry it. The tree carries it
as a statement of the language, the way it carries `Try` and `Throw`, and
the label is a statement too.

- **A label is a name and a colon.** The name is of letters, of digits and
  of the underscore, and it may begin with a digit: `1abc:` is a label. A
  line that ends with a colon and is not one of them holds no action, and
  the message of the dialect is "This line does not contain a recognized
  action.\n     Specifically: a-b:" -- the message of `done :` and of `done:
  FileAppend "x", "*"` too.
- **The parameter of a `Goto` is not an expression.** It is the name of a
  label, and it is read as the text of it: `Goto "done"` looks for a label
  that is called `"done"`, with the quotes, and `Goto done` looks for the
  label `done`. The name of a label does not know its case, and the text of
  the parameter is what the failure names.
- **The `Goto` needs one parameter and it takes one.** The load refuses the
  one that has none -- "\"Goto\" requires at least 1 parameter. Specifically:
  Goto" -- and the one that has more -- "\"Goto\" accepts at most 1
  parameter.\n     Specifically: Goto a, b".
- **A label belongs to the scope it is written in.** The scope of the
  script, or the scope of a function or of a method. A label of another
  scope is not found in the current one: "Label not found in current scope.
  Specifically: later" is the message of the dialect.
- **The jump may go to a label of the block it is in, or of a block around
  it.** A label of a block that does not enclose the jump is refused with
  "A Goto must not jump into a block that doesn't enclose it.".
- **The failure of a `Goto` ends the script, and a catch does not take
  it.** The tree has a kind of failure for it -- `RuntimeFailure::Fatal` --
  and it is not given to the functions of the error either.
- **A label that is written twice in the same scope is refused at the
  load.** "Duplicate label.\n     Specifically: done" is the message of the
  dialect, and it names the line of the second label.
- **`IsLabel` asks the scope that runs.** It answers one when the label is
  there and zero when it is not, and a name that is empty is a name that is
  not there.

One thing the tree does and the binary of v2.0.19 does not: the binary
never comes back from a `Goto` that leaves a block which has statements
after it, and it never comes back from the parenthesis of the parameter --
`Goto(later)` hangs it too. The tree jumps and goes on, the way the
documentation of the dialect says: "Goto jumps to the specified label and
continues execution."

The comparison of the tree with the binary is in
`egm-review/compare_goto.py` (34 cases): 31 are the same, and the three
that are not are the hang of the binary.

## 73. The class types are classes of the dialect, and the call of one is the call of v2

Measured on the binary of v2.0.19 on 2026-10-31: the dialect has
twenty-nine class types, and a script reads every one of them as the
class. The table of the surface carries them now, with a kind of their
own, and the tree reads them the way the binary does.

- **A class type is a name that a script reads as the class.** `x := Map`
  answers a value whose class is "Class", and the thirty cases that were
  measured are the same in the binary and in the tree.
- **The `Hotkey` is the exception.** The name is a function of v2 -- `x :=
  Hotkey` answers a "Func" -- and the class of a hotkey is the class of
  the object that the function makes. The tree looks the built-in table
  before the classes, so that the two do not fight for the name.
- **A class is a value, and the call of it makes an object of that class.**
  `c := Map; c()` makes a map, the way `Map()` does, and the sixteen
  classes that were measured are the same in the binary and in the tree.
- **The number of the arguments of a constructor is the one of the binary,
  and the refusal names the class.** `classes::CONSTRUCTORS` carries the
  arity of every constructor and the two names that go in the `What` and
  in the `Extra` of the refusal: `ComObject()` answers "Too few parameters
  passed to function." with the `Extra` "ComObject.Call", `Class(1)`
  answers "Too many parameters passed to function." with the `What`
  "Object.Call", and the `Array` takes any number of arguments, because

  carry them.** The `ComObject` and the `ComValue` are classes of the

  is refused with "Parameter #1 of ClipboardAll.Prototype.__New requires a
  Number, but received a String.", the address of nothing is refused with
  "Parameter #1 of ClipboardAll.Prototype.__New is invalid.", and an
  address without a size is refused with "Parameter #2 of
  ClipboardAll.Prototype.__New must not be omitted in this case.".
- **The word `class` and the class type `Class` are told apart by what
  follows.** A name makes a declaration -- `class Foo { }` and `Class Foo
  { }` are both of them -- and anything else makes a call of the class:
  `Class(1)` is a call, and the binary refuses it at the run.
- **A class that the dialect does not make is refused with the message of
  the dialect.** The `File`, the `Func` and the `Enumerator` are not made

## 74. A text of v2 is between double quotes or between single quotes

Measured on the binary of v2.0.19 on 2026-10-31: the text of v2 has two
kinds of quote, and the tree took only the double one. A script that wrote
a text between single quotes did not parse.

- **The two kinds of quote are the same.** The escape of the dialect is the
  backtick in the two of them -- `` `n `` is a line break and `` `" `` is a
  double quote -- and a backslash is a backslash in the two of them: the
  path of a file is written with it, and v2 does not read it as an escape.
- **The doubled quote is not an escape.** `x := "it""s"` is two texts side
  by side, and v2 refuses it with "Missing space or operator before this.
  Specifically: "s"". The tree joined the two, and it joined them without
  a space too.
- **A text does not cross a line.** The text ends at the end of the line,
  and a text that is not closed before it is refused with the quote that is
  not closed and the line that holds it: "Missing """
     Specifically: x
  := "abc" for the double quote, and "Missing "'"" for the single one.
- **Two values side by side are one value, and the space between them is
  what makes it so.** `x := "a" "b"` is "ab", and `x := "a""b"` is refused
  with "Missing space or operator before this.\n     Specifically: "b"". The name
  of the value that came too close is the text of it, with the quote that
  was written.
- **The token keeps the quote that was written.** The source of the script
  is rebuilt from the tokens, and the rebuild says the truth: `Goto 'done'`
  looks for a label that is called `'done'`, with the quotes, the way
  `Goto "done"` looks for one that is called `"done"`.

The rule of the dialect lives in the lexer, in the one place where the
texts are read, and the v1 -- which has only the double quote -- will leave
it out there.

  file of every frame, the line of it, the source of the line and the name
  of the function, and the script of the runner has no file: the file of
  every frame is empty. The section 104 says the whole of it.

## 97. The continuation section of v2

Measured on the binary of v2.0.19 on 2026-10-31, and read in the
documentation of v2 (`Scripts.htm` and `v2-changes.htm`): the lines between
a `(` and a `)` that are both at the start of a line are merged with the
line above them, and the tree refused every one of them.

- **A line that begins with a `(` is a section.** The line is an expression
  and not a section when it carries a `)` of its own after the opening one:
  the string of the option `Join` is the only one that may carry a
  parenthesis. A section that is an expression is a statement whose value is
  not used, and the tree reads it as one: `Node::Expression`.
- **The section continues the last line that has code.** The blank lines and
  the comments between the line and the section are of no account, and a
  directive takes the rest of its line, so the section that follows one is
  part of its argument.
- **A space is put between the line and the section when the line ends with
  a name.** A name is a letter, a digit or the underscore, and the quote of a
  text is not a name: `x := 1` and then the section with `2` answers 12, and
  `x := "a"` and then the section with `"b"` is refused with "Missing space
  or operator before this." and the text.
- **The newlines of the section are spaces in an expression, and they are
  kept inside a text.** The quotes of a text that holds a section are
  literal characters, and the closing quote has to be on the line of the
  closing parenthesis.
- **The options of the section are on the line of the `(`.** They are
  separated by spaces, and a comment ends them: `Join` (with no string of
  its own, or with the string that follows its name), `LTrim`, `LTrim0`,
  `RTrim0`, `Comments` -- also `Comment`, `Com` and `C` -- and the accent,
  which is a backtick and makes the backtick of the text a literal
  character. The option that v2 does not know is refused at the load:
  "Invalid option." and the name of it.
- **The indentation of the first line goes from the lines.** The leading
  whitespace of the lines follows the indentation of the first one, and a
  line that is indented less is left as it is. The option `LTrim` takes all
  of it away and `LTrim0` keeps it, and the trailing whitespace of the
  lines is removed unless `RTrim0` keeps it.
- **The section that is not closed is refused at the load.** The refusal is
  "Missing \")\"" and the text it merged with the line above, and the
  newline that ends that text is not a part of it.
- **The text that a refusal names is the text of the source, and the newline
  of the line is not a part of it.** The block that the error printer of v2
  writes ends with a newline of its own, and the message is the block
  without it. The rest of the line is named when a value came too close, and
  the statement is named when a bracket is not there.
- **The escape of a space is a space.** `` `s `` is a space in v2.0.19, and
  the tree refused it: `"a`sb"` was "asb" and it is "a b".

## 98. The increment, and the assignment that is not one

Measured on the binary of v2.0.19 on 2026-10-31: the increment may be a
statement of its own, and it may be of a property and of an item, and the
left side of an assignment is a variable, a property or an item -- and
every other value is refused with a reason of its own.

- **The increment may be a statement.** `x++` and `++x` are statements, and
  they write to the variable that is before them. The postfix answers the
  value that was there, and the prefix answers the one that is there.
- **The increment of a property and of an item writes to them.** `x.a++`,
  `x[1]++` and `m["a"]++` write to the property and to the item, and the
  value of a call cannot be written to.
- **The space tells the increment apart from the concat.** `x++` is the
  increment of `x`, and `x ++` is a call of `x` with the argument `++`. A
  line that ends with `++` does not continue on the next one, and the
  operator of the increment binds to the value that is before it.
- **The increment of a value that cannot be written is refused at the
  load.** The refusal is "Invalid assignment." and the source of the
  operator: "Invalid assignment." and "++".
- **The number at the left of an assignment is refused at the parse.** The
  refusal is "Syntax error." and the number: "Syntax error." and "1". The
  number that carries no point is the one that is refused there, and the
  exponent is not a point: `1`, `1e3` and `0x10` are refused there.
- **The number that carries a point is refused by the assignment.** The
  refusal is "Invalid assignment." and the operator and the value:
  "Invalid assignment." and ":= 2". The compound operators refuse the
  number the same way, and the point at the end of the number is not a
  point of a number.
- **The number with a point at its end holds no action.** The refusal is
  "This line does not contain a recognized action." and the line: the
  point is the dot of a member that is not there.
- **The array and the text at the start of a statement hold no action.**
  The refusal is "This line does not contain a recognized action." and the
  line: `[1] := 2` and `"a" := 2` name the whole line.
- **The statement that begins with a unary operator is not one that the
  tree reads.** v2 reads `-x := 2` as the compound assignment of `x`, and
  `-1 := 2` as a line that holds no action; the tree refuses the line with
  "Unexpected \"-\"". The number that begins with a point is a number in
  v2 and the tree does not read it: ".5" is refused with "Unexpected
  \".\"".

## 99. The static declaration of v2

Measured on the binary of v2.0.19 on 2026-10-31: `static` is the third
kind of declaration of v2, and the name lives in the storage of the
function that declares it.

- **The static belongs to the function that declares it.** The name is one
  of the function for its whole body, and the value is kept between the
  calls: the function that counts with a static answers 1 and then 2.
- **The static shadows a global inside the function.** The global of the
  same name lives in the scope of the script, and the function reads its
  own.
- **The value of the declaration runs once.** The declaration runs its
  value the first time that declaration is reached, and not on every call:
  the function that declares `static count := 5` and counts answers 6 and
  then 7. A declaration that the function does not reach on the first call
  runs its value on the call that reaches it, and a declaration that comes
  after another one of the same name runs its value as well.
- **The static of a method belongs to the method.** Two instances of the
  same class share it, and the static of a recursion is the same one in
  every turn of it.
- **The static at the top level is refused.** It has no function to live
  in, and the whole declaration is named with it: "Unexpected declaration."
  and "static count := 1".
- **The static may not name a parameter of the function.** The refusal is
  "This static variable declaration conflicts with an existing parameter."
  and the name of it.
- **The bare `static` inside a function is a declaration with no name.**
  It is accepted, and the bare `local` is refused. The bare `static` at
  the top level is a corner of v2: the binary reads the line that follows
  as a declaration and refuses it, and it crashes when there is no line
  after it. The tree refuses it with "Unexpected declaration." and
  "static".

The comparison of the tree with the binary is in
`egm-review/compare_static_declaration.py` (19 cases, none of them

## 100. The number of v2 may begin with a point

Measured on the binary of v2.0.19 on 2026-10-31: the numbers of v2 may
begin with a point, and the point that follows a value is the point of a
member.

- **The number may begin with a point.** `.5` is the number 0.5, and it is
  0.5 in every place where a number may be written: in an assignment, in a
  sum, in a group, in an array, in the arguments of a call and in the value

- **The name of a property of the literal of an object may be a whole

  refuses it with "Invalid property name in object literal.": `{1.5: 1}` and
  `{.5: 1}` are both refused, and so is the text.
- **The point alone is not a number.** The family of the statement that
  begins with an operator is the next block, and it says what the v2 says
  about it.

## 101. The statement that begins with an operator

## 102. The family of the loop

Measured on the binary of v2.0.19 on 2026-10-31: the loop of v2 is one
statement with five shapes, and the word that follows the `Loop` says
which one it is.

- **The word that follows the `Loop` is a name of the kind when the line
  goes on after it.** The kinds are `Files`, `Reg`, `Read` and `Parse`,
  and the name of the kind is part of the statement: `Loop Read` is not
  the loop of a count with the variable `Read` in it. The word is the
  count of the loop when the line ends there: `Loop Read` alone is a
  loop that counts the value of the variable `Read`, and `Loop Read` with
  the body on the next line is that loop too.
- **The command of a kind checks its parameters when the script loads.**
  The parameter that is not there is named: "Parameter #1 required" and
  the head of the statement, the text that was written before the body --
  `Loop Read {` is "Loop Read ". The list of the parameters that is empty
  says so in the words of the command: "\"Loop Read\" requires at least 1
  parameter." and the line.
- **The command of a kind names itself when it is not complete.** The body
  that is not there is "Unexpected \"Loop Read\"", and the name of the kind
  is the one that the script wrote: "Loop read" is "Loop read ".
- **The command of a kind takes the parameters that it takes.** `Loop
  Read`, `Loop Files` and `Loop Reg` take two, and `Loop Parse` takes
  three. The one that is written too many says so at the load: "\"Loop
  Read\" accepts at most 2 parameters." and the head with the first
  parameter.
- **The count of the loop is not a name of a kind.** A comma after the
  count says that the type of the loop is not a valid one: "Invalid loop
  type." and the line. The comma of a call is not there: "Function calls
  require a space or \"(\".  Use comma only between parameters." and the
  line.
- **The loop without a count goes on until a break.** The v2 has no bound
  of its own, and the tree has one: the count of the statements. The body
  may be empty, and the count of the statements is the bound that still
  moves.
- **The fields of the loop that parses are the characters of the text.**
  The delimiters that are not there make every character a field of its
  own, and the spaces are fields too. The characters that are not wanted
  at the ends of a field are taken away from it.
- **The line of the file is `A_LoopReadLine`, and `A_LoopField` is the
  field of the loop that parses.** The variables of the loops are there
  before the first loop runs: the index is zero and the others are empty.
- **The second parameter of `Loop Read` is not carried yet.** The v2 keeps
  that file open for the duration of the loop and the `FileAppend` of the
  body writes to it; the tree reads the file and writes nothing.

## 109. The name that the script builds

## 114. The name and the space and the parenthesis is a command

- **A definition with a space is not a definition:** the v2 refuses it at

## 133. The words of the v2, and the reason of each one

  another one. The `--dialect=v1` asks for the legacy dialect, and the
  parser and the runtime carry it: the tables of the v2 are the tables of
  the v2, and the v1 has a table of its own names.
- **The shape of a parameter is a column of the table of the built-ins.**
  It is the value of an expression, the reference that the caller passes,
  the name of a variable of the script, or the name of the variable that
  the built-in writes into. The flag of the table of v2 -- the place of
  the first parameter that is written back -- is read out of that column
  now, and `builtins::reference_parameters` is the column turned into the
  places of the parameters.
- **The `=` of the v1 and the `=` of the v2 are the same.** Measured on
  the binary of v2.0.19 on 2026-11-01: `"ABC" = "abc"` is one and
  `"ABC" == "abc"` is zero, in the v2 as in the v1. The plan of the v1
  dialect said that the v2 had them the other way round, and the binary
  says otherwise. The comparison of the tree does not change.
- **The variables of a function are local in the v1 as in the v2.**
  Measured on the binary of v1.1.37.02 on 2026-11-01: a variable that a
  function writes is not seen outside of it, and the word `global` is
  what makes it so. The plan of the v1 dialect said that the variables
  were global by default, and the binary says otherwise.
- **The parameters of a command of the v1 are texts.** Measured on the
  binary of v1.1.37.02 on 2026-11-01: `FileAppend, hello, *` writes
  `hello`, `FileAppend, "hello", *` writes `"hello"` with the quotes,
  and the shape of the parameter says what the text is -- the value of an
  expression, the name of a variable of the script, or the name of the
  variable that the command writes into. `StringLen, n, hello` is five
  when `hello` is a variable of the script, and zero when it is not: the
  second parameter of that command is the *name* of a variable.
- **The surface is per dialect.** `--surface --dialect=v1` prints the
  names of the v1 and where each one stands here, and the names of the v1
  are the ones that the dialect spells: `A_Clipboard` and not
  `Clipboard`.

The probes that measured the rules are in
`egm-review/probe_v1_semantics.py` (24 cases), in
`egm-review/probe_v1_semantics2.py` (30 cases) and in
`egm-review/probe_v1_semantics3.py` (21 cases).

## 140. The table of the v1, and the command whose parameters are texts

Measured on the binary of v1.1.37.02 on 2026-11-01. This is the phase F1
of the plan of the v1 dialect.

- **The table of the v1 is a table of its own.** It has 203 rows: the
  names of the v1 that the tree answers, with the shape of their
  parameters and the handler that answers them. A name that the v1 has
  and the v2 does not is a row of the v1, and a name that the two share
  points at the handler of the v2. The table is written by
  `egm-review/patch_v1_table.py`, and the pending table follows it with
  `egm-review/patch_v1_pending.py`.
- **The command of the v1 writes into a variable of the script.** The
  shape of the parameter says what it is: the value of an expression, the
  name of a variable of the script, or the name of the variable that the
  command writes into. The `Output` of the v1 is the `Reference` of the
  v2, and the runtime hands the handler the alias of that variable.
- **The command whose answer goes into a variable borrows the handler of
  the v2.** `EnvGet, name, value` is the `EnvGet` of the v2 with the
  answer written into the first parameter, and so are the other twenty
  commands of that family. The `InputBox` of the v1 writes the text of
  the user and not the object of the v2, and the `Run` writes the pid of
  the program into the last parameter.
- **The name of a command that the dialect does not have is a line that
  holds no action.** The v1 refuses it at the load, and it names the
  line: "This line does not contain a recognized action.\n     Specifically:
  NoSuchCommand, 1".
- **The substitution of a parameter of the v1 is the variable of the
  script, and the environment is what is left.** Measured on the binary
  of v1.1.37.02 on 2026-11-01: `%TEMP%` is the value of the variable
  `TEMP` when the script has one, and the value of the environment
  otherwise.
- **The surface of the v1 is 384 names: 220 answer with a value, 106 are
  refused and 58 are pending.** The refusals are the names of Windows,
  and the pending are the names that the tree does not carry yet.

## 141. The grammar of the v1, and the line that continues on a comma

Measured on the binary of v1.1.37.02 on 2026-11-01. This is the phase F2
of the plan of the v1 dialect.

- **The body of a construct of the v1 is one statement.** The `if`, the
  `else`, the `while` and the `loop` take the statement that comes after
  them, and not a block: `if (1)` and then `FileAppend, yes, *` on the
  next line is an `if` with a body. The tree already read the body of a
  construct without braces, and the v1 is that.
- **The count of the loop of the v1 comes after a comma.** `Loop, 3` is a
  loop of three turns, and the kinds of the loop of the v1 (`Files`,
  `Reg`, `Read` and `Parse`) are not carried yet.
- **The line of a command of the v1 continues only after a comma.** The
  v2 continues a line that ends with any operator, and the v1 does not:
  the star of `FileAppend, hello, *` is the end of the command, and the
  line that follows it is another statement. The rule of the v2 was
  swallowing the line of the label that came after the command.
- **The hotstring of the v1 is a statement.** `::btw::by the way` is a
  hotstring, and the trigger of it is between the two pairs of colons and
  the action is what comes after them.
- **The directives are the ones of the dialect.** The v1 knows fifteen
  directives that the v2 does not know, and the name of a directive that
  the dialect does not know is a line that holds no action, and it is
  refused at the load.

## 142. The semantics of the v1: the blank that is not a failure

Measured on the binary of v1.1.37.02 on 2026-11-01. This is the phase F3
of the plan of the v1 dialect.

- **A value that is not there is blank, and it is not a failure.** The
  variable of the script that has no value, the division by zero and the
  name that the environment does not have are all blank in the v1. The v2
  refuses them, and the tree keeps that for the v2.
- **The sum of a text and a number is a concatenation.** `"5" + 1` is
  `51` in the v1, and the sum of two numbers is a number. The v2 refuses
  the operator that wants a number after a literal text, and the tree
  keeps that for the v2 too: in the v1 the sum is the one operator that
  may follow a literal text.
- **The substitution of a parameter of the v1 is the variable of the
  script, and the environment is what is left.** A name that has no value
  at all is substituted by nothing, and not by the text of the name: the
  `%TEMP%` of a script that has no variable of that name and no
  environment of that name is empty.
- **The directive `#NoEnv` turns the lookup of the environment off.** The
  variable of the script is still there, and the `%TEMP%` of a script
  that has no variable of that name is empty.

## 143. The surface asks the dialect, and the variables of the v1 answer

Measured on the binary of v1.1.37.02 on 2026-11-02. This is the first
block of the phase F5 of the plan of the v1 dialect, and it fixes two
things that the surface of the v1 was saying wrong.

- **A directive is a name that the dialect knows, and the runtime
  answers it.** The surface was asking the lexer, and the lexer carries
  the directives of the v2: the fifteen directives that the v1 has and
  the v2 does not were "pending" while the tree was answering them. The
  table of the directives is now the same one that the run reads
  (`runtime::refusal_of_directive`), so a directive that the runtime
  refuses with a reason is a refusal and not a pending: the `#MaxMem` of
  the v1 is refused with "the memory limits are not carried by this
  runtime." and the `#Persistent` is the case that the runner already
  is.
- **The name of a built-in variable keeps the spelling of its
  dialect.** The table of the v2 carries the name with the prefix and
  the table of the v1 carries it with it too, and the surface was
  taking the prefix away before it asked. The dialect is the one that
  knows the name that its own table holds.
- **The twenty-nine built-in variables of the v1 that the v2 does not
  have are carried.** Measured on the binary on 2026-11-02: the
  `A_AutoTrim` is `On`, the `A_FormatFloat` is `0.6`, the
  `A_FormatInteger` is `D`, the `A_DefaultGui` is `1`, the
  `A_IsUnicode` is `1`, the `A_BatchLines` and the `A_NumBatchLines`
  are `10ms`, the `A_StringCaseSense` is `Off`, and the names that the
  tree has no thing for -- the `A_Gui` and the rest, the `A_ThisMenu`
  and the rest, the `A_CaretX` and the `A_CaretY` -- are empty, the
  way the v1 answers them when there is none.
- **The two of them that are about the machine are refused with the
  reason.** The `A_OSType` is `WIN32_NT` in the v1, and the
  `A_IPAddress1` is the address of the first adapter of the machine,
  and this runtime answers neither: the first is refused as a name of
  Windows, and the second as a desktop that does not know the address.
- **The built-in variables of the v1 are read-only.** The write of one
  of them is refused with the message of the v1 -- "Not allowed as an
  output variable." with the name of the variable -- and the only one
  that a script may write is the `A_Args`.
- **The parity test runs for the two dialects.** The question of
  `tests/surface.rs` is the one that the `--surface` command asks, and
  it asks the dialect: the names of the v1 that the tree does not carry
  yet are the fifteen of the pending table of the v1, and a name that
  moves between the tables breaks the build of the test.

The numbers: the surface of the v1 has **384** entries -- **261** answer
with a value, **108** are refused and **15** are pending. The surface of
the v2 did not move: **828** entries, **637** values, **191** refusals
and no pending.

## 144. The v1 has no classes, and the name of a variable is a name

Measured on the binary of v1.1.37.02 on 2026-11-02. This is the second
block of the phase F5 of the plan of the v1 dialect, and it carries seven
names that the v1 has and the v2 does not.

- **The `IsSet` of the v1 asks for the name of the variable, and the
  `IsFunc` asks for the value.** `IsSet(y)` asks whether the variable `y`
  has a value, and not whether the value of `y` is the name of a variable:
  with `y := "nosuchname"`, the answer is 1. The `IsFunc` answers 1 for a
  function of the script, 2 for a built-in and 0 for anything else. The
  dialect says which of its functions asks for a name, and the runtime
  hands the name over instead of the value.
- **The v1 has no class types.** The name `Func` of the v1 is a function
  and not the class of the v2, and the call of it makes the value of the
  function of the script: it carries the name of it, the number of its
  parameters, and the call of it is the call of the function.
- **The object of the v1 has no class.** The `__Class` of it is empty,
  and the literal `{}` is the same object. The kind of an object without
  a class is `Object` in the messages of the tree.
- **The backslash of a command of the v1 is a letter of the text of the
  parameter.** `FileRead, text, C:\temp\x.txt` is a command of the v1,
  and the binary accepts it. The path of a file is the use that every
  command of the v1 has, and the path of Windows has backslashes in it.
  The v2 refuses the backslash outside of a text.
- **The `FileReadLine` of the v1 wants three parameters**, and the answer
  is the n-th line of the file, without the line ending, and it is empty
  when the file has no such line.
- **The `Input` of the v1 asks the user with a dialogue**, and the title
  is the prompt of it.

The numbers: the surface of the v1 has **384** entries -- **268** answer
with a value, **108** are refused and **8** are pending. The surface of
the v2 did not move.

## 145. The surface is JSON for the CI, and the text is for a human

The plan of the v1 dialect asks for the JSON: "the JSON, for the CI, is a
piece of F5". The runner answers it with `--surface --json`, and the
dialect is the one that `--dialect` names.

The JSON carries the numbers of the summary -- the dialect, the total, the
values, the refusals and the pending -- and the state of every name: the
name, the kind, the class of a method, the state and the reason of the
names that are refused or that are pending. The text of the surface is
the same thing for a human, and it is what the command prints when the
JSON is not asked for.

## 147. The legacy assignment of the v1 is a text, and the `AutoTrim` trims it

Measured on the binary of v1.1.37.02 on 2026-11-02.

- **The right side of the legacy assignment is a text and not an
  expression.** `x = 5 + 3` leaves `x` at "5 + 3", `x = "abc"` leaves it at
  `"abc"` with the quotes that were written, `x = (5+3)` leaves it at
  "(5+3)", and `x = ` leaves it at nothing. The tree had it as an
  expression, and it answered 8 for `x = 5 + 3`.
- **The text is a whole number when it is one in base ten.** `x = 5` leaves
  `x` at the number 5, and `x = 5.5` leaves it at the text "5.5", and `x =
  0x10` leaves it at the text "0x10". The `SetFormat, Integer, H` says
  which one it is: the text of `x = 255` is "0xFF", and the text of `x =
  5.5` is "5.5" and not "5.50".
- **The text is trimmed, and the `AutoTrim` trims the text that comes from a
  substitution.** `x =    hello` leaves `x` at "hello" even with the
  `AutoTrim` off, and `x = %z%` leaves `x` at the value of `z` without the
  spaces that come before it and the spaces that come after it when the
  `AutoTrim` is on. The parameters of a command are not trimmed by it.
- **The `AutoTrim` is a command, and the `A_AutoTrim` says which one is in
  force.** The command is "On" when the script begins, and the value that it
  does not know is refused with "Parameter #1 invalid.".
- **The text of the script is the text.** `FileAppend, [  pad  ], *` writes
  `[  pad  ]`, and the tokens alone would keep one space. The parser keeps
  the lines of the source for this.
- **The substitution finds the built-in variables.** `%A_AutoTrim%` is "On".
- **The equal sign does not write a member.** `o.a = 5` is refused at the
  load with "This line does not contain a recognized action.".

One thing is measured and not carried yet: the arithmetic of the v1 with a
text. The tree concatenates when an operand is a text, and the v1 does not:
the text that is written on the left of a `+` makes it a concatenation, the
text that is written on the right of it makes the result blank, and the
value of a variable is converted to a number when it can be. The block that
carries it comes next.
