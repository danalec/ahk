# The v2.0.31: what the release changed, and what the tree does about it

The record of the move of the tree from the dialect of AutoHotkey v2.0.19
to the dialect of the **v2.0.31**. It
is a record, not a guide: it says what was measured, what the two
releases answer, and what the tree carries.

## The method

Two binaries were compared:

| The release | The binary | The documentation |
|---|---|---|
| 2.0.19 | `%TEMP%\ahk-v2-measure\AutoHotkey64.exe` | `AutoHotkey.chm`, decompiled in `chm/` |
| 2.0.31 | `%TEMP%\ahk-v2-measure-2.0.31\AutoHotkey64.exe` | `AutoHotkey.chm`, decompiled in `chm/` |

The measurements were made, with the instrument of
`scripts/measure-surface-2.0.31.py` for the surface, and with the
scripts of `scripts/` that compare two binaries case by case for the
behaviour. A case that opens a dialog is killed after a few seconds and
reported as such: a load error of the binary is a dialog.

## The surface did not move

| What | 2.0.19 | 2.0.31 |
|---|---|---|
| The pages of the library of the documentation | 356 | 356 |
| The built-in variables of the documentation | the same | the same |
| The names that are new | -- | **none** |
| The names that are gone | -- | **none** |
| The arities of the names that changed | -- | **the same** |

The documentation of the two releases names the same names, and the
binary of the 2.0.31 accepts the same number of parameters for each of
them. The table of the tree moved from `ahk-v2.0.19.surface.tsv` to
`ahk-v2.0.31.surface.tsv`, and the rows of it are the same rows.

## What the documentation of the release changed

Seventy-one pages of the library changed their syntax lines. Most of the
change is a rename of a parameter -- the `Control` of the `Control*`
family is the `ControlID` now, the `Hwnd` is the `HWND` -- and a rename
is not a change of the binary.

Four are changes of the lines of the documentation, and the
measurement of the day says that the behaviour of the binary did not move
with them:

| The name | The 2.0.19 | The 2.0.31 |
|---|---|---|
| `CoordMode`, `Critical`, `DetectHiddenText`, `DetectHiddenWindows`, `FileEncoding` | a command | a command that answers the **previous setting** |
| The properties of the class `Error` -- `Extra`, `File`, `Line`, `Message`, `Stack`, `What` | read only | with setters |
| `Error.Call(Message, What, Extra)` | -- | there |
| `ControlAddItem`, `ControlFindItem` | nothing | the **index** of the item |

## The measurement of the behaviours that the documentation changed

The table above is the diff of the two documentations. The binaries are
another matter, and the measurement of the day is the one that says what
they do. Every case that was run answers the same in the two binaries:
the v2.0.19 answers the previous setting already, it writes the
properties of the Error already, it has the Error.Call already, and
it answers the index of the item already. The four changes of the
documentation are the lines of the documentation.

### The method of the measurement


Each case is a script of its own. The script is run with the switch
`/ErrorStdOut`:

```
AutoHotkey64.exe /ErrorStdOut <the script>
```

The switch puts the refusal of the loader on the standard error instead
of a dialog, and it says nothing about the failures of the run: those
are caught by the script itself.

Every statement of a case that can fail is inside a `try` that catches
the error and writes the message of it, because the message of a failure
is what a dialog hides:

```ahk
Ask(label, fn) {
    global out
    try {
        r := fn.Call()
        if IsSet(r)
            out .= label " => [" r "]  (type=" Type(r) ")" Chr(10)
        else
            out .= label " => (no value)" Chr(10)
    } catch as e {
        out .= label " => ERROR: " e.Message "  (What=" e.What ", Line=" e.Line ")" Chr(10)
    }
}
```

The answer is written to a file beside the script, and not to the pipe of
the process: a case that is killed loses what is in the pipe, and the
file keeps it.

```ahk
outPath := A_ScriptDir "\" A_ScriptName ".out"
Emit() {
    global out
    FileAppend out, outPath, "UTF-8"
    out := ""
}
```

Every script ends with `ExitApp(0)`, and every script registers a
handler of the failures that the `try` of the case did not catch:

```ahk
OnError Report
Report(exc, ThrownBack) {
    global out
    out .= "UNCAUGHT: " exc.Message "  (What=" exc.What ", Line=" exc.Line ")" Chr(10)
    Emit()
    ExitApp(0)
}
```

The handler takes two parameters. A handler of one parameter is refused
by the binary with `Error: Invalid callback function.`, and the refusal
is a dialog of its own.

The process is given twelve seconds. A case that is still up after that
is killed, and the text of the dialog it left behind is read with the
automation of Windows and written down: the dialog is part of the answer
of a case, and a case that opens one is reported as one.

### The answers of the two binaries


| The case | The v2.0.19 answers | The v2.0.31 answers | The tree has to |
|---|---|---|---|
| `CoordMode("Mouse", "Screen")` | `Client` -- the mode that was there before | `Client` | nothing: the tree answers the previous mode already |
| `Critical(true)` | `0` -- the value that was there before | `0` | done: the tree answers `0` |
| `DetectHiddenText(false)` | `1` -- the value that was there before | `1` | nothing: the tree answers the previous value already |
| `DetectHiddenWindows(true)` | `0` -- the value that was there before | `0` | nothing: the tree answers the previous value already |
| `FileEncoding("UTF-8")` | `CP0` -- the encoding that was there before | `CP0` | done: the tree answers the previous encoding |
| `FileEncoding()` -- no value | refused when the script loads: `Too few parameters passed to function.` | the same | nothing |
| `e.Message := ...` | written | written | nothing |
| `e.What := ...` | written | written | nothing |
| `e.Extra := ...` | written | written | nothing |
| `e.File := ...` | written | written | a test is left to write |
| `e.Line := ...` | written | written | a test is left to write |
| `e.Stack := ...` | written | written | a test is left to write |
| `Error.Call(msg, what, extra)` | the object is made | the object is made | nothing: the tree makes the object of the error |
| `ControlAddItem(text, hwnd)` | `2` -- the index of the new entry | `2` | nothing: the tree answers the index |
| `ControlFindItem(text, hwnd)` | `2`, and `Failed` when the entry is not there | the same | nothing: the tree fails with `Failed` |
| the name `Control` of the second parameter | the binary cannot be asked | the binary cannot be asked | nothing: the tree does not name the parameters of the builtins |

### The cases, one by one

### `CoordMode`

The documentation of the v2.0.31 gives the syntax of the command as
`PrevRelativeTo := CoordMode(TargetType, RelativeTo)`, and the one of
the v2.0.19 gives it as `CoordMode TargetType , RelativeTo`. The
question of the case is whether the answer of the binary changed with
the documentation.

The script of the case (`c01-coordmode.ahk`):

```ahk
Ask("CoordMode(Mouse,Screen)  [prev]", () => CoordMode("Mouse", "Screen"))
Ask("CoordMode(Mouse,Client)  [prev]", () => CoordMode("Mouse", "Client"))
Ask("CoordMode(Mouse)         [prev, one arg]", () => CoordMode("Mouse"))
Ask("CoordMode(Pixel,Window)  [prev]", () => CoordMode("Pixel", "Window"))
Ask("CoordMode(Mouse,Screen)  [prev, again]", () => CoordMode("Mouse", "Screen"))
```

The v2.0.19 answers:

```
CoordMode(Mouse,Screen)  [prev] => [Client]  (type=String)
CoordMode(Mouse,Client)  [prev] => [Screen]  (type=String)
CoordMode(Mouse)         [prev, one arg] => [Client]  (type=String)
CoordMode(Pixel,Window)  [prev] => [Client]  (type=String)
CoordMode(Mouse,Screen)  [prev, again] => [Screen]  (type=String)
```

The v2.0.31 answers the same:

```
CoordMode(Mouse,Screen)  [prev] => [Client]  (type=String)
CoordMode(Mouse,Client)  [prev] => [Screen]  (type=String)
CoordMode(Mouse)         [prev, one arg] => [Client]  (type=String)
CoordMode(Pixel,Window)  [prev] => [Client]  (type=String)
CoordMode(Mouse,Screen)  [prev, again] => [Screen]  (type=String)
```

**The two are the same.** The v2.0.19 answers the previous setting too,
and the mode that is not used is `Client`, and the second parameter left
out means `Screen`.

The tree answers the previous mode as well -- `settings::coord_mode`
swaps the mode and answers the one that was there -- so the tree has
nothing to do about this one.

#### The built-in variable `A_CoordMode`

Both CHMs say that the built-in variable `A_CoordMode` holds the mode of
each target, and both binaries refuse the name with a dialog:

```
Warning: This global variable appears to never be assigned a value.

Specifically: A_CoordMode
```

The dialog is the warning of the loader, and it is the same in the two
versions. The case was killed after twelve seconds, and the text above
is what the dialog said. This is a divergence of the documentation from
the binary that is the same in the two versions, and not a change
between them.

### The name of the parameter of the `Control` family

The documentation of the v2.0.31 names the second parameter of the
`Control` family `ControlID`, and the one of the v2.0.19 names it
`Control`. Nothing of the run can tell the two apart: the name of a
parameter is not in the answer of anything, and a binary is not asked
about it.

The tree does not name the parameters of its builtins -- the row of
`ControlAddItem` in the table of the builtins carries the shape of the
parameter and nothing else -- and the surface of the tree is already
against the v2.0.31. The tree has nothing to do about this one.

### What the tree has to do about them

The measurement says this: the documentation of the v2.0.31 changed the
syntax lines of these names and not their behaviour. Every case that was
run answers the same in the two binaries, and the only difference the
diff of the two documentations shows that a run can see is the name of
the parameter of the `Control` family, which no answer shows. The tree is
measured against the v2.0.19, and the two binaries agree on every case
of this list, so the version of the reference does not change what the
tree has to do.

The tree answers like the release on all of them,:

- `CoordMode` answers the mode that was there before, and the mode that
  is not used is `Client`.
- `Critical` answers `0`: the tree runs one script in one thread, and
  that thread is never critical, so the setting that was there before is
  always `0`.
- `DetectHiddenText` answers the value that was there before, and the
  value that is not used is `1`.
- `DetectHiddenWindows` answers the value that was there before, and the
  value that is not used is `0`.
- `FileEncoding` answers the encoding that was there before, and the
  encoding that is not used is `CP0`.
- The six properties of the class `Error` are written, and the setters of
  `File`, of `Line` and of `Stack` are own properties of the object and
  go through the same write as the three that are tested.
- `Error.Call` makes the object of the error.
- `ControlAddItem` answers the index of the new entry, and
  `ControlFindItem` fails with `Failed` when the entry is not there.

What is left is a test of the three setters of the `Error` that the tree
does not test -- the ones of `File`, of `Line` and of `Stack` -- and the
names of the class value of the `Error`, which do not name `Call` among
them the way the class value of the `Map` does. That is a question of
the names and not of the behaviour.

The name of the parameter of the `Control` family is a question of the
documentation alone: the tree does not name the parameters of its
builtins, and the surface of the tree is already against the v2.0.31.

The built-in variable `A_CoordMode` is the fifth thing: both
documentations name it and both binaries warn that it is a variable that
is never assigned a value. The tree has the `A_` variables of the v1 --
`A_CoordModeMouse`, `A_CoordModePixel` and the others -- and not the
object of the v2; that is a question of the dialect and not of the
version, and this measurement does not settle it.

**The tree answers like the release on all of them.** Measured on the tree:

| The case | The tree answers |
|---|---|
| `x := CoordMode("Mouse", "Screen")` | `Client` -- the previous setting |
| `x := DetectHiddenText("On")` | `1` -- the previous setting |
| `x := DetectHiddenWindows("On")` | `0` -- the previous setting |
| `x := FileEncoding("UTF-8")` | `CP0` -- the previous setting; the tree answers it |
| `e := Error("m")` ; `e.Message := "another"` | `another` |
| `e := Error("m", "w", "x")` ; `e.What := "w2"` | `w2` |
| `e := Error.Call("m", "w", "x")` | the message, the what and the extra |
| `x := Critical("On")` | `0` -- the previous setting; the tree carries the name |

The `Control*` family is the one that the tree refuses with a reason of
the machine: it asks about a window of another program, and the desktop
of the tree is not Windows.

The `FileEncoding` and the `Critical` are the two that the tree did not
answer like the release on the day of the table above, and it answers
them now: the handler of `FileEncoding` reads the encoding that was
there before and answers it, and the handler of `Critical` answers `0`,
because the tree runs one script in one thread and that thread is never
critical. The measurement of the day says that the binaries answer the
same in the two versions.

## What the tree does with the release

1. **The version.** The dialect is the v2.0.31: the tree answers
   `A_AhkVersion` with `2.0.31`, and `#Requires AutoHotkey v2.0.31` is
   met while `#Requires AutoHotkey v2.0.32` is not.
2. **The tables.** The tables of the surface, of the pending names, of
   the operators and of the areas carry the name of the release: they are
   `ahk-v2.0.31.*` in `crates/ahk/reference/`, and the tests read them
   when they are compiled.
3. **The documents.** The documents that name the dialect name the
   release now. The notes that record a measurement keep the version
   they measured: a measurement of the 2.0.19 is a measurement of the
   2.0.19, and the tree does not pretend otherwise.
4. **The behaviour.** The tree answers like the release on the cases
   above, and the two cases where it does not are the ones the release
   refuses with a dialog.

The next release of the tree is measured the same way: the binary, the
documentation, and the change log of the release.

## The classes of the controls of a window

The classes of the controls are nested classes of the class `Gui`, and the
binaries carry twenty-five of them as values: `Type(Gui.Control)` answers
"Class" on the binary of the v2.0.19 and on the binary of the v2.0.31,
alike. The tree refused them all, and `Type(Gui.Control)` was refused
with *"This value of type \"Class\" has no property named \"Control\"."*.

The gap was **the same in the two releases**: it was a hole of the tree and
not a change of the release. The tree carried the methods of five of the
classes -- `Gui.Control`, `Gui.ListView`, `Gui.Menu`, `Gui.StatusBar` and
`Gui.TreeView` -- and the class `Gui` had the `AddButton`, the `AddEdit`
and the other ways of making a control; what was missing was the class
value.

The classes are carried now: the class value of the `Gui` owns them, and
each one of them is a class of its own, with the base that the binary
gives it. The tables of their members were read out of the binary and the tree was carrying the wrong ones: the row of the
`Gui.ListView` was the table of the `Gui.TreeView`, and the row of the
`Gui.StatusBar` was the table of the `Gui.ListView`.

The instruments of the measurement are `scripts/probe-classes.py` and
`scripts/probe-gui-classes.py`, and the hole is written down in
`docs/ahk-gaps-report.md`, in the section of the holes of the v2 that are
known.
